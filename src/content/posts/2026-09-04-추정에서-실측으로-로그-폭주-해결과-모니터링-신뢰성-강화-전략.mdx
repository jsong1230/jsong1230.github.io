# [Dev Log] 로그 폭주 해결과 '추정'이 아닌 '실측'의 시스템 구축

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 가장 경계해야 할 것 중 하나는 **"아마 잘 돌아가고 있겠지"**라는 막연한 추정입니다. 특히 인프라 운영과 모니터링 단계에서 '추정'은 곧 '사각지대'를 의미합니다. 오늘은 메타디움 익스플로러 스택의 로그 최적화 작업과 백업 알림 시스템의 신뢰성을 높인 과정을 정리해 보려 합니다.

---

## 1. 로그 폭주 억제: "신호(Signal)와 소음(Noise)의 분리"

최근 특정 컨테이너(`sync-consumer`)에서 하루에 약 9.8GB라는 엄청난 양의 로그가 쏟아지는 현상을 발견했습니다. 로그 보존 기간이 너무 짧아, 정작 알림이 왔을 때 원인을 분석하기 위한 로그가 이미 덮어씌워져 사라진 상태였습니다.

### 문제 분석 및 해결
실측 결과, 로그의 대부분은 `p6spy`가 기록하는 SQL 쿼리와 Spring Batch의 메타데이터였습니다. 이는 진단을 위한 '신호'라기보다 시스템을 무겁게 만드는 '소음'에 가까웠습니다.

- **SQL 로그 차단**: `p6spy` 설정을 최상위 `decorator` 키로 옮겨 정확히 비활성화했습니다. (기존에는 설정 키 위치가 잘못되어 `true`임에도 작동하지 않았던 '죽은 설정' 상태였습니다.)
- **ANSI 컬러 코드 제거**: Docker json 로그 파일에 `ESC[32m` 같은 ANSI 이스케이프 문자가 그대로 들어가 용량을 차지하고 `grep` 검색을 방해하고 있었습니다. 이를 `enabled: never`로 변경하여 텍스트 순도를 높였습니다.

### 기술적 결정: 로그 앵커의 분리
모든 컨테이너의 로그 용량을 늘리는 것은 위험합니다. 과거 404GB 로그 사건의 교훈으로, 공용 설정은 보수적으로 유지하되 **조사가 빈번한 `sync-consumer`만 별도의 앵커(`x-logging-verbose`)로 분리**하여 1GB까지 확장했습니다. 

이제 로그 발생량이 일 400MB 수준으로 줄어들어, 약 2.5일치의 로그를 안정적으로 보존하며 알림 발생 시 충분한 역추적이 가능해졌습니다.

## 2. 알림 시스템: "갔을 것(추정)" $\rightarrow$ "갔다(실측)"

백업 시스템의 알림 로직에서도 중요한 인사이트를 얻었습니다. 기존 `notify()` 함수는 `curl`의 종료 코드(exit code)만 확인했습니다. 하지만 텔레그램 API는 토큰이 잘못되어도 HTTP 응답 본문에 `{"ok":false}`를 담아 보내며, `curl` 자체는 성공(rc=0)으로 반환합니다.

즉, **알림이 실패했는데 시스템은 성공했다고 믿는 '침묵의 실패'** 상태였던 것입니다. 실제로 상용 API 호스트 일부가 죽은 토큰으로 수개월간 알림을 보내지 못했던 사례가 이를 증명합니다.

### 개선 사항
- **응답 본문 파싱**: 이제 `ok` 필드를 직접 파싱하여 실제 발송 성공 여부를 판정합니다.
- **발송 이력 로그화**: `~/.backup-send.log`를 신설하여 발송 결과를 한 줄 이력으로 남깁니다.
- **검증 로직 강화**: `morning-check` 스크립트가 단순히 "성공했을 것"이라고 추측하는 대신, 로그 파일의 실측 기록을 읽어 **"완료 1건 발송 확인(실측)"**이라고 보고하도록 변경했습니다.

```bash
# 개선된 판정 로직의 핵심
# 기존: curl rc=0 -> "성공 추정"
# 변경: 응답 본문 "ok":true 확인 -> 로그 기록 -> morning-check가 로그 읽기 -> "실측 성공"
```

또한, 보안 강화를 위해 `curl`의 `stderr`가 로그에 섞여 봇 토큰이 유출될 가능성을 원천 차단하기 위해 `2>/dev/null` 처리를 추가하는 등 '코드 경화' 작업을 병행했습니다.
