# [DevLog] 데이터의 흐름으로 기록하는 나의 성장 궤적: 대시보드 업데이트와 인사이트

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한(Jeffrey)입니다.

엔지니어로서 20년 넘게 커리어를 쌓아오며 제가 가장 중요하게 생각하는 것 중 하나는 '가시화(Visualization)'입니다. 단순히 코드를 짜는 것을 넘어, 내가 어떤 방향으로 나아가고 있는지, 현재 나의 리소스가 어디에 집중되고 있는지를 데이터로 확인하는 습관은 기술적 결정의 정밀도를 높여줍니다.

오늘은 개인 대시보드(`jsong1230.github.io`)의 데이터를 업데이트하며, 최근 나의 작업 패턴을 복기해 보았습니다.

### 🛠 오늘의 작업: 대시보드 데이터 동기화

오늘의 작업은 단순해 보이지만 의미 있는 `chore: Update dashboard data`였습니다. `dashboard.json` 파일을 통해 여러 레포지토리의 활동량(Activity)과 최근 커밋 메시지를 업데이트했습니다.

```json
// 변경 전
"last_msg": "[main] fix(probe): cert 만료일 읽기도 3회 재시도 — 단발 실패로 ",
"commits_7d": 18,

// 변경 후
"last_msg": "런북: 정상 상태 메모리 기준선(10/10 실측)",
"commits_7d": 3,
```

단순한 JSON 업데이트 같지만, 이 diff 속에는 최근 제가 집중하고 있는 기술적 고민들이 고스란히 담겨 있습니다.

### 🔍 기술적 인사이트: '런북'과 '기준선'의 중요성

이번 업데이트에서 특히 눈에 띄는 부분은 `validator` 레포지토리의 커밋 메시지입니다: **"런북: 정상 상태 메모리 기준선(10/10 실측)"**.

블록체인 밸리데이터나 복잡한 분산 시스템을 운영하다 보면, '장애'를 정의하는 것이 가장 어렵습니다. 단순히 CPU 점유율이 높다고 해서 장애라고 할 수 있을까요? 정답은 **'정상 상태의 기준선(Baseline)'**이 있느냐 없느냐에 달려 있습니다.

실측 데이터를 바탕으로 기준선을 설정하고 이를 런북(Runbook)에 명시하는 작업은, 장애 발생 시 엔지니어가 당황하지 않고 객관적인 지표에 근거해 의사결정을 내리게 합니다. 씨피랩스에서도 늘 강조하는 부분이지만, 고도화된 시스템일수록 '감'이 아닌 '데이터'에 기반한 운영 체계를 갖추는 것이 핵심입니다.

### 💡 마치며: 기록이 만드는 복리 효과

`claude-agent`나 `booksummary` 같은 개인 프로젝트들의 활동 지표가 꾸준히 업데이트되는 것을 보며, 기술적 탐구와 인문학적 소양(독서)의 균형이 결국 더 나은 아키텍처를 설계하는 밑거름이 된다는 것을 다시금 느낍니다.

- **`claude-agent`**: AI 에이전트의 로그 스캔 및 효율화 작업 (기술적 깊이)
- **`booksummary`**: 에리히 프롬의 「소유냐 존재냐」 정리 (철학적 확장)

매일의 작은 커밋과 데이터 업데이트는 당장은 티가 나지 않지만, 시간이 흐르면 거대한 성장 곡선을 그리는 '복리 효과'를 가져옵니다. 여러분도 자신만의 대시보드를 통해 성장의 궤적을 기록해 보시는 건 어떨까요?

오늘도 기록하며 성장합니다. 🚀
