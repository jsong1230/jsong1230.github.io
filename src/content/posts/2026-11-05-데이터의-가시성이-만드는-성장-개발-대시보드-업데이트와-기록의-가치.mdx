# [Dev Log] 데이터의 시각화, 그리고 기록이 주는 힘: 대시보드 업데이트를 통해 본 개발자의 루틴

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 20년 넘게 커리어를 쌓아오며 제가 가장 중요하게 생각하는 것 중 하나는 '가시성(Visibility)'입니다. 복잡한 블록체인 인프라나 Web3 프로젝트를 리딩하다 보면, 현재 우리가 어디에 있고 어떤 속도로 움직이고 있는지를 객관적인 데이터로 확인하는 것이 얼마나 중요한지 매번 깨닫게 됩니다.

오늘은 제 개인 개발 대시보드의 데이터를 업데이트하는 간단한 작업을 진행했습니다. 단순한 `chore` 작업처럼 보일 수 있지만, 이 과정에서 느낀 몇 가지 인사이트를 공유하고자 합니다.

### 🛠 오늘의 작업: 개발 활동 데이터 동기화

오늘 진행한 작업은 `src/data/dashboard.json` 파일을 업데이트하여 최근의 리포지토리 활동 내역을 반영하는 것이었습니다. 

```json
// 변경 전
"generated_at": "2026-11-03T23:00:01.856Z",

// 변경 후
"generated_at": "2026-11-04T23:00:01.688Z",
```

단순히 날짜를 바꾸는 것이 아니라, `heritageradio`, `validator`, `metadium-explorer-stack` 등 제가 관리하는 여러 프로젝트의 커밋 횟수와 마지막 메시지를 동기화했습니다. 특히 이번 업데이트에서는 `validator`와 `metadium-explorer-stack` 같은 핵심 인프라 관련 리포지토리의 활동이 구체적으로 반영되었습니다.

### 💡 기술적 결정과 인사이트

**1. 정적 데이터 기반의 가벼운 대시보드 전략**
실시간 API를 통해 데이터를 가져올 수도 있겠지만, 저는 의도적으로 JSON 파일을 통해 데이터를 관리하고 이를 커밋하는 방식을 택했습니다. 이는 두 가지 이점이 있습니다. 첫째, 대시보드 로딩 속도가 극단적으로 빠릅니다. 둘째, 데이터의 변경 이력이 Git 히스토리에 남기 때문에, 시간이 흐른 뒤 제가 어떤 시기에 어떤 프로젝트에 집중했는지 '타임라인' 형태로 복기할 수 있습니다.

**2. '커밋 메시지'라는 기록의 가치**
diff 내용을 살펴보면 흥미로운 부분이 있습니다.
- `validator`: "런북: v2.2.3·v2.2.4 보류 기록"
- `claude-agent`: "ops: revoke stale mykeepin admin... from did-auth RDS SG"

단순히 코드를 수정하는 것을 넘어, 런북(Runbook)을 업데이트하거나 보안 그룹(SG)의 오래된 권한을 회수하는 등의 운영(Ops) 작업들이 기록되어 있습니다. Web3와 DID 분야의 엔지니어에게 가장 위험한 것은 '기억에 의존하는 운영'입니다. 이렇게 사소한 변경 사항이라도 명확한 메시지로 남기는 습관이 결국 시스템의 안정성으로 이어집니다.

### 🚀 마치며

많은 분이 "매일 커밋하는 것이 정말 의미가 있느냐"고 묻곤 합니다. 하지만 저는 그렇게 생각하지 않습니다. `commits_30d` 수치가 올라가는 것은 단순히 숫자의 증가가 아니라, 제가 매일 문제를 해결하고 시스템을 개선했다는 '성장의 증거'이기 때문입니다.

씨피랩스에서도 팀원들과 함께 이러한 기록의 문화를 만들어가고 있습니다. 기술적 깊이는 결국 꾸준한 기록과 복기에서 나오기 때문입니다. 여러분의 대시보드에는 오늘 어떤 기록이 남았나요?
