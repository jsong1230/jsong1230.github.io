# [Dev Log] 데이터 자동화와 기록의 힘: 대시보드 업데이트를 통해 본 개발자의 루틴

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

개발자에게 있어 '기록'은 단순히 과거를 남기는 것이 아니라, 현재의 생산성을 측정하고 미래의 방향성을 설정하는 중요한 지표가 됩니다. 저는 개인적인 개발 활동과 프로젝트 진행 상황을 한눈에 파악하기 위해 자체적인 대시보드를 운영하고 있는데요. 오늘은 이 대시보드의 데이터를 업데이트하며 느낀 몇 가지 생각들을 공유해보려 합니다.

### 🛠️ 오늘의 작업: 대시보드 데이터 갱신 (chore: Update dashboard data)

오늘 진행한 작업은 겉보기에는 단순한 `dashboard.json` 파일의 수정입니다. 하지만 이 JSON 데이터 뒤에는 제가 관리하는 여러 레포지토리의 커밋 로그, 활동량, 최신 메시지들이 자동화된 프로세스를 통해 집계되어 반영되고 있습니다.

이번 업데이트에서 특히 흥미로웠던 부분은 제가 현재 집중하고 있는 프로젝트들의 '맥락'이 고스란히 드러난다는 점입니다.

```diff
- "last_msg": "[admin] docs(api): 등록 가이드 — 코너별 연도 자리(0000/19NN) 표 +"
+ "last_msg": "[admin] fix(audit-notify): cron 에 ssh-agent 가 없다 — 자동화 키 + EC2"
```

위의 diff 내용을 보면 `heritageradio` 프로젝트에서 단순한 문서 작업(docs)을 넘어, 실제 인프라의 자동화 이슈(`cron` 환경에서의 `ssh-agent` 부재 문제)를 해결한 흔적이 보입니다. 

엔지니어로서 가장 까다로우면서도 해결했을 때 쾌감이 큰 지점이 바로 이런 '환경 설정의 틈새'를 메우는 일입니다. 특히 EC2 환경에서 자동화 키 관리와 셸 환경의 차이로 발생하는 문제는 실무 경험이 없으면 디버깅에 꽤 많은 시간을 허비하게 되죠. 20년 넘게 엔지니어링을 해왔지만, 여전히 이런 로우레벨의 환경 설정 문제는 늘 새로운 배움을 줍니다.

### 💡 기술적 결정과 인사이트: 왜 '데이터화' 하는가?

단순히 Git Graph를 보는 것만으로도 충분할 텐데, 왜 굳이 JSON 형태로 데이터를 추출해 대시보드를 만들까요?

1. **메타 인지(Meta-cognition)의 강화**: `commits_7d`, `commits_30d`와 같은 수치를 통해 제가 어떤 프로젝트에 과몰입하고 있는지, 혹은 방치하고 있는 프로젝트는 무엇인지 객관적으로 파악할 수 있습니다.
2. **맥락의 보존**: `last_msg`를 통해 며칠 전 내가 어떤 고민을 하며 코드를 짰는지 빠르게 리마인드할 수 있습니다. 이는 컨텍스트 스위칭 비용을 줄여주는 효과적인 장치가 됩니다.
3. **자동화의 습관화**: 데이터를 수동으로 적는 것이 아니라, 스크립트를 통해 업데이트하는 프로세스 자체가 하나의 작은 '제품'을 만드는 과정입니다.

### 마치며

오늘의 커밋은 비록 `chore`라는 이름의 단순 작업이었지만, 그 안에는 인프라 트러블슈팅의 결과와 개인적인 성장 기록이 담겨 있습니다. 

씨피랩스에서도 저는 팀원들에게 항상 "측정할 수 없으면 개선할 수 없다"고 강조합니다. 거창한 KPI가 아니더라도, 나만의 작은 지표를 만들고 기록하는 습관이 결국 기술적 깊이를 만드는 밑거름이 된다고 믿습니다.

여러분은 자신의 성장 궤적을 어떻게 기록하고 계신가요?
