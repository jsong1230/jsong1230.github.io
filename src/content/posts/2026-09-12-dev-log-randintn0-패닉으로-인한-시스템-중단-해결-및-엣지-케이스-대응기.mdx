# [Dev Log] 0.1%의 엣지 케이스가 불러온 1,000건의 실패: `rand.Intn(0)` 패닉 해결기

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey)입니다.

엔지니어로서 가장 당혹스러운 순간 중 하나는 "분명히 잘 돌아가고 있었는데, 특정 조건에서 시스템이 통째로 멈추는 현상"을 발견했을 때입니다. 특히 그 원인이 아주 사소한 함수 호출 하나 때문이었다면 더욱 그렇겠죠. 오늘 저는 메인넷의 DID 발급 프로세스를 간헐적으로 중단시켰던 치명적인 패닉(Panic) 버그를 잡고, 이를 통해 얻은 인사이트를 공유하고자 합니다.

### 1. 문제의 발단: 사라진 노드와 `rand.Intn(0)`

우리가 운영하는 `go-delegator`는 여러 RPC 노드 중 하나를 무작위로 선택해 요청을 보냅니다. 평소에는 문제가 없지만, 노드가 연속적으로 실패하면 가용 노드 수(`availLen`)를 줄여 효율적으로 관리하도록 설계되어 있었습니다.

그런데 여기서 치명적인 엣지 케이스가 발생했습니다. **가용 노드 수가 0이 되는 순간, `rand.Intn(0)`이 호출되며 Go 런타임 패닉이 발생한 것입니다.**

```go
// 문제의 흐름
// 1. 노드 연속 실패 -> removeNode 호출 -> availLen 감소
// 2. availLen == 0 도달
// 3. randomURL() 내에서 rand.Intn(0) 호출 -> PANIC!
```

메인넷의 경우 RPC URL이 하나뿐인 설정이 많았습니다. 그 단일 노드가 잠시 흔들리면 `availLen`이 0이 되고, 이후 재기동 전까지 모든 DID 발급 요청이 "Internal Error(Panic)"로 응답하며 서비스가 완전히 마비되는 구조였습니다. 로그를 분석해 보니 약 8일간 1,000건에 가까운 실패가 발생했더군요. 아무도 몰랐던 '조용한 재앙'이었습니다.

### 2. 기술적 결정: "영구적 포기보다는 다시 시도하는 편이 낫다"

단순히 패닉을 막는 것을 넘어, 시스템의 회복 탄력성(Resilience)을 높이기 위해 세 가지 전략을 적용했습니다.

**첫째, 가용 노드가 0이면 전체 목록을 리셋합니다.**
노드가 죽었다고 표시되었더라도 시간이 지나면 복구되었을 가능성이 큽니다. 완전히 포기하고 멈추는 것보다, 경고 로그를 남기고 다시 전체 목록에서 시도하는 것이 서비스 가용성 측면에서 훨씬 유리합니다.

**둘째, `removeNode` 시 최소 한 개의 노드는 남깁니다.**
애초에 `availLen`이 0이 되지 않도록 방어막을 쳤습니다. 또한, 읽기/쓰기 경쟁 상태(Race Condition)를 방지하기 위해 `availMu` 뮤텍스로 보호 로직을 강화했습니다.

**셋째, 설정 경로의 유연성을 확보했습니다.**
그동안 상대 경로(`./conf/config.json`)에 묶여 있어 패키지 단위 테스트가 `init()` 단계에서 패닉이 나며 실행조차 되지 않았습니다. 이를 해결하기 위해 환경 변수 `DELEGATOR_CONFIG`로 경로를 덮어쓸 수 있게 수정했습니다.

```go
// common/delegator_config.go
if p := os.Getenv("DELEGATOR_CONFIG"); p != "" {
    configPath = p
}
```
이제 `DELEGATOR_CONFIG=/tmp/x.json go test ./rpc/`와 같이 임시 설정을 주입해 완벽한 회귀 테스트를 수행할 수 있게 되었습니다.

### 3. 인프라의 재현성: `git bundle`을 이용한 서브모듈 동기화

코드 수정 외에 인프라 관리 측면에서도 중요한 작업을 진행했습니다. 특정 개발 환경(189)에서 SSH 자격 증명 문제로 `git submodule update`가 실패하는 상황이었습니다. 서버에 배포 키를 심는 것은 보안상 찜찜한 일이죠.

이를 해결하기 위해 **`git bundle`**을 활용한 동기화 스크립트를 작성했습니다. 로컬에서 필요한 커밋 객체만 번들 파일로 만들어 전송하고, 서버에서는 이 번들을 통해 체크아웃하는 방식입니다. 자격 증명 없이도 정확한 커밋 포인터를 맞출 수 있어 재현성을 완벽히 복구했습니다.

### 마치며: 엔지니어의 인사이트

이번 작업의 핵심은 **"실패를 어떻게 처리할 것인가"**에 있었습니다. 
1. **Fail-safe 설계**: 어떤 상황에서도 시스템이 패닉으로 완전히 멈추지 않게 해야 합니다.
2. **Observability**: 패닉이 `recover`로 잡혀 "Internal Error"로 나갈 때, 그것이 단순 오류인지 시스템 붕괴인지 구분할 수 있는 로그가 필수적입니다.
3. **Testability**: 테스트가 불가능한 코드는 수정할 수 없는 코드와 같습니다. 환경 변수 하나로 테스트 환경을 분리한 것이 이번 버그를 완벽히 검증하는 열쇠가 되었습니다.

작은 `Intn(0)` 하나가 서비스 전체를 흔들 수 있다는 점을 다시금 깨달은 하루였습니다. 오늘도 더 단단한 시스템을 위해 고민합니다.
