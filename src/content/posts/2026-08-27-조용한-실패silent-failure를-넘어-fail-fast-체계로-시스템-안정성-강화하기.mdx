# [Dev Log] "조용한 실패"를 걷어내고, Fail-Fast 체계로 전환하기

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 가장 경계해야 할 상황이 무엇일까요? 시스템이 완전히 멈춰서 에러 로그가 쏟아지는 상황일까요? 아닙니다. 진짜 무서운 것은 **'시스템은 정상이라고 말하는데, 실제로는 아무 일도 일어나지 않고 있는 상태'**, 즉 **조용한 실패(Silent Failure)**입니다.

오늘 저는 `heritageradio` 프로젝트의 Tier3 S5-C 작업을 통해, 오랫동안 시스템 내부에 잠복해 있던 이 '조용한 fallback' 구조를 완전히 제거하는 작업을 진행했습니다.

### 1. 문제의 핵심: "눈을 감은" 모니터링 도구
그동안 저희 시스템은 `dated` 방식(날짜 기반)과 `flat` 방식(단일 경로)이라는 두 가지 경로를 모두 지원해 왔습니다. 하지만 최근 `flat` 세그먼트를 전량 삭제하며 이제는 `dated` 방식만이 유일한 정답이 된 상태입니다.

문제는 기존 코드 곳곳에 **"만약 설정 파일이 없거나 로드에 실패하면, 조용히 옛날 방식(flat)으로 돌아가라"**는 fallback 로직이 남아 있었다는 점입니다. 

이 구조가 위험한 이유는 검증 도구(canary, hourly verify)들이 이 로직을 그대로 따랐기 때문입니다.
- **Canary**: 라이브러리 로드에 실패하면 `is_dated_era()`를 그냥 `false`로 반환했습니다. 결과적으로 핵심 검사 2개가 통째로 스킵되었음에도 화면에는 **"✅ 정상"**이 찍혔습니다. 모니터링 도구가 스스로 눈을 감고 있었던 셈입니다.
- **Hourly Verify**: 검증 대상 목록이 비어 있으면 아무것도 수행하지 않고 **"verify OK"**를 출력했습니다.

### 2. 기술적 결정: Fail-Fast로의 전환
저는 이번 리팩터링에서 단순한 코드 삭제를 넘어, **Fail-Fast(즉시 실패)** 원칙을 적용했습니다. "어떻게든 돌아가게 만드는 것"보다 "잘못되었다면 즉시 멈추고 알리는 것"이 운영 안정성 측면에서 훨씬 유리하기 때문입니다.

**주요 변경 사항:**
- **라이브러리 필수화**: `hls_dated_lib.sh`가 없으면 즉시 `exit 1`로 중단합니다.
- **가드 로직 추가**: `verify_prod_sync_hourly.sh`에 `GROUPS_RUN` 가드를 추가하여, 단 하나의 그룹도 실행되지 않았다면 FAIL을 반환하게 했습니다.
- **명시적 옵션 강제**: `verify_prod_sync.py`에서 `--dated` 옵션을 필수화하여, 의도치 않은 동작 가능성을 차단했습니다.

```bash
# 변경 전: 조용히 통과하거나 flat으로 동작
# 변경 후: lib 부재 시 rc=1 즉시 중단, 옵션 누락 시 rc=2
```

### 3. 런타임의 함정: "호출은 있는데 정의가 없다?"
리팩터링 과정에서 흥미로운 버그 하나를 발견했습니다. 주말 동기화 스크립트(`sync_today_cycle1_weekend.sh`)에서 `run_with_retry` 함수를 호출하고 있었는데, 정작 해당 파일 내에는 함수 정의가 누락되어 있었습니다.

이것은 `shellcheck` 같은 정적 분석 도구로도 잡기 어려운 **런타임 문제**였습니다. 다른 템플릿 코드를 복사해 오면서 호출부는 가져왔지만, 정의부는 빠뜨린 전형적인 실수였죠. 만약 이를 발견하지 못했다면, 주말 새벽 00:05분에 `command not found` 에러와 함께 동기화 작업이 즉시 종료되었을 것입니다.

결국 **"호출 vs 정의" 전수 대조**라는 원시적이지만 확실한 방법으로 이를 잡아냈고, 3회 시도/30초 백오프 로직을 추가해 자가 복구 능력을 갖추도록 정합성을 맞췄습니다.

### 4. 마치며: 엔지니어의 집요함에 대하여
오늘 작업의 핵심은 **"불확실성의 제거"**였습니다. 8월 17일에 겪었던 GC(Garbage Collection) 미작동 사건처럼, 실행 권한(`exec bit`) 하나가 누락되어 시스템이 멈췄던 경험은 저에게 큰 교훈을 주었습니다.

운영 환경에서 '적당히'는 없습니다. 특히 인프라와 배포 스크립트 영역에서는 **"명확하게 성공하거나, 요란하게 실패하거나"** 둘 중 하나여야 합니다. 그래야만 우리는 시스템을 신뢰할 수 있고, 문제가 생겼을 때 즉각적으로 대응할 수 있습니다.

오늘 밤 22:00, 새롭게 적용된 `dated FLIP` 경로가 첫 가동을 시작합니다. Fail-Fast 체계가 구축되었으니, 만약 문제가 생기더라도 텔레그램 알림이 요란하게 울리겠지요. 역설적이게도 저는 그 알람이 울리지 않는 고요한 밤을 기대하며 퇴근합니다.
