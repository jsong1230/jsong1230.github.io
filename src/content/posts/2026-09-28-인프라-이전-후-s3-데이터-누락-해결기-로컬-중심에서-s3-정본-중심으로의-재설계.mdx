# [Dev Log] 인프라 이전 후 깨진 동기화 고리 찾기: S3 정본 중심의 재설계

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 가장 당혹스러운 순간 중 하나는 "분명히 자동화되어 있는데, 데이터가 누락되고 있을 때"입니다. 최근 EC2로 인프라를 이전한 후, 오디오 파일 동기화 과정에서 예상치 못한 '데이터 갭'이 발생했습니다. 오늘은 이 문제를 어떻게 진단하고, 어떤 기술적 결정으로 해결했는지 공유하려 합니다.

### 1. 문제의 발견: "분명히 올렸는데 왜 없지?"

기존의 `sync_to_aws_prod.sh` 스크립트는 호스트의 로컬 디렉터리(`audio/*`)를 기준으로 프로덕션(Prod) S3 버킷에 동기화하는 구조였습니다. 과거에는 로컬에 모든 데이터가 상주했기에 문제가 없었지만, EC2 이전 후 **로컬의 성격이 '저장소'에서 '캐시'로 변하면서** 설계의 전제가 깨졌습니다.

실측 결과, 다음과 같은 심각한 누락이 발견되었습니다.
- **로컬 캐시 의존성:** 로컬 정리 스크립트가 동기화 작업보다 먼저 실행되면, 파일이 Prod로 올라가기도 전에 삭제되어 영영 유실되는 케이스가 발생했습니다.
- **합성 프로세스와의 충돌:** 오디오 합성 중 '잘린 파일'이 올라가는 것을 막기 위해 동기화 단계를 통째로 skip 하도록 설정했는데, 합성 체인이 길어지자 Prod 데이터가 계속 밀렸습니다. (실측 결과 1,486편 누락)
- **프리페치 게이트 오류:** 어드민 등록 음원이 로컬에만 존재하고 Dev S3에 올라가지 않아, 빌드 시스템이 이를 '없음'으로 판단하는 현상이 있었습니다. (77편 누락)

### 2. 기술적 결정: '로컬'이 아닌 'Dev S3'를 정본(Source of Truth)으로

문제를 해결하기 위해 저는 로컬 캐시에 의존하던 기존 방식을 버리고, **Dev S3 $\rightarrow$ Prod S3**로 이어지는 파이프라인을 구축하기로 했습니다. 새롭게 작성한 `audio_s3_reconcile.py`의 핵심 로직은 다음과 같습니다.

#### A) 로컬 $\rightarrow$ Dev S3 (안전한 업로드)
단순히 모든 파일을 올리는 것이 아니라, **수정 후 30분이 지난 파일만** 올리도록 제한했습니다. 
> `A) 로컬 → dev S3 : 수정 30분 지난 파일만(합성·loudnorm 중인 파일 제외)`

이는 파일이 `in-place`로 쓰여지고 있는 도중에 불완전한 파일이 S3에 올라가는 것을 방지하기 위한 안전장치입니다.

#### B) Dev S3 $\rightarrow$ Prod S3 (효율적인 동기화)
Dev S3를 정본으로 삼아 Prod와 대조합니다. 여기서 흥미로운 점은 **비용 최적화**입니다. S3 간 복사를 기본으로 하되, 만약 동일한 파일이 로컬에 온전히 존재한다면 로컬에서 직접 업로드합니다. 이는 Glacier IR(Immediate Retrieval) 인출 비용을 회피하기 위한 전략적 선택입니다.

### 3. 인사이트: 인프라의 변화는 '가정'을 다시 검토하게 한다

이번 작업에서 배운 점은 **"인프라의 물리적 구조가 바뀌면, 기존에 당연하게 여겼던 소프트웨어의 가정(Assumption)을 모두 의심해야 한다"**는 것입니다. 

과거에는 `로컬 == 전체 데이터`라는 가정이 성립했지만, 클라우드 네이티브 환경으로 옮겨가며 `로컬 == 휘발성 캐시`로 성격이 변했습니다. 이 간극을 메우지 않고 코드만 수정했다면, 데이터 누락은 계속되었을 것이고 결국 서비스 신뢰도로 이어졌을 것입니다.

단순한 스크립트 수정처럼 보이지만, 데이터의 흐름(Data Flow)을 다시 정의하고 '정본'이 어디에 있어야 하는지를 명확히 하는 과정이었습니다. 앞으로도 씨피랩스에서 더 견고하고 확장 가능한 아키텍처를 만들어가겠습니다.
