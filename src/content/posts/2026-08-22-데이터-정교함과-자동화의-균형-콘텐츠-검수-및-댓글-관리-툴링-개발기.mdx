# [Dev Log] 데이터의 정교함과 자동화의 균형: 콘텐츠 검수 게이트와 댓글 관리 툴링

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey)입니다.

개발자의 일상은 거대한 아키텍처를 설계하는 일뿐만 아니라, 아주 작은 수치 하나를 조정해 전체의 품질을 끌어올리는 '디테일의 싸움'이기도 합니다. 오늘은 제가 진행한 두 가지 서로 다른 성격의 작업—콘텐츠 데이터의 정밀 검수와 유튜브 커뮤니티 관리 자동화—를 통해 느낀 인사이트를 공유하고자 합니다.

### 1. 텍스트 데이터의 '예상 시간'과 '실제 자수' 사이의 괴리

최근 진행 중인 헤리티지 라디오 프로젝트에서 60편의 대본 보강 작업을 마쳤습니다. 여기서 흥미로운 기술적 도전은 **'낭독 시간의 정밀한 제어'**였습니다. 

보통 텍스트의 길이를 자수로 제한하면 시간이 일정할 것이라 생각하지만, 실제로는 그렇지 않습니다. 마크업 비율이나 문장 구조에 따라 같은 자수라도 낭독 시간은 수십 초씩 차이가 납니다. 저는 이를 해결하기 위해 두 단계의 필터링 시스템을 구축했습니다.

- **1차 여과 (BAND):** 원시 자수 기준의 빠른 필터링
- **최종 판정 (Review):** 예상 낭독 초(second) 기준의 정밀 검수

작업 중 원시 자수 상한선을 통과했음에도 예상 음성 시간이 상한(581~582s)을 초과하는 사례가 3건 발생했습니다. 원인을 분석해 보니 마크업 비율이 편마다 23~25%로 흔들리고 있었더군요. 결국 저는 다음과 같이 코드를 수정하며 기준을 명확히 했습니다.

```python
# 상한은 review_narration_scripts.py 보다 보수적으로 잡는다. 
# 원시 상한은 통과했으나 예상 음성이 상한을 넘긴 편이 발생함.
# 최종 판정은 언제나 review 쪽(예상 초)이다. 이 값은 1차 여과용.
BAND = {"YASA_STORY": (3550, 3760), "JOSEON_STORY": (3380, 3580), "DRAMA_NOVEL": (3420, 3620)}
```

데이터를 다룰 때 **'대리 지표(Proxy Metric, 여기서는 자수)'**와 **'실제 목표 지표(Target Metric, 여기서는 낭독 시간)'**가 일치하지 않을 수 있음을 다시 한번 깨달았습니다. 항상 최종 판정 기준이 무엇인지 명시하고, 대리 지표는 보수적으로 운용하는 것이 안전합니다.

### 2. 자동화의 적정선: '보고'는 자동화하되 '판단'은 인간의 영역으로

또 다른 작업으로는 `booksummary` 프로젝트의 구독자 댓글 관리 툴을 개발했습니다. 매일 수많은 댓글을 일일이 확인하는 것은 비효율적이지만, 그렇다고 답글 게시까지 완전히 자동화하는 것은 위험합니다. 특히 혐오 표현이나 섬세한 감정 케어가 필요한 커뮤니티 관리에서는 더욱 그렇습니다.

그래서 저는 **'보고(Reporting) $\rightarrow$ 판단(Judgment) $\rightarrow$ 실행(Execution)'**의 파이프라인을 설계했습니다.

1. **`check_new_comments.py`**: 미답변 댓글만 추출하여 리포트 생성 (Cron으로 매일 자동 실행)
2. **인간/AI의 판단**: 리포트를 보고 답글 문안 작성
3. **`reply_to_comments.py`**: 작성된 문안을 일괄 게시 (`--dry-run` 옵션으로 최종 확인 후 `--apply`)

특히 보안상의 이유로 YouTube 인증 토큰이 포함된 `secrets/` 폴더를 Git에 올리지 않기 때문에, 클라우드 에이전트 대신 로컬 Cron 방식을 채택하는 실무적인 결정도 내렸습니다.

### 마치며: 엔지니어의 시선으로 본 '완결성'

오늘의 작업들을 관통하는 키워드는 **'검수 게이트(Inspection Gate)'**입니다. 텍스트 데이터든, 커뮤니티의 소통이든, 단순히 '돌아가는 코드'를 만드는 것을 넘어 '품질이 보장되는 프로세스'를 만드는 것이 CTO로서 제가 지향하는 엔지니어링입니다.

정교한 기준을 세우고, 그 기준이 흔들릴 때 빠르게 피드백 루프를 수정하는 것. 그것이 결국 사용자에게 닿는 최종 결과물의 완성도를 결정짓는다고 믿습니다.
