# 인프라 최적화와 관찰 가능성: 비용 절감부터 알림 식별까지

안녕하세요, 씨피랩스의 CTO 송주한입니다.

엔지니어로서 가장 보람찬 순간 중 하나는 기술적 결정이 실제 수치(비용 절감)로 이어지거나, 모호했던 운영 프로세스가 명확한 시스템으로 정립될 때입니다. 오늘은 제가 진행한 몇 가지 인프라 작업과 운영 개선 사항을 공유해 보려 합니다.

### 1. ElastiCache에서 EC2 자체 호스팅으로: 실리를 챙긴 마이그레이션

최근 `heritageradio` 프로젝트의 Redis 호스팅 방식을 관리형 서비스인 ElastiCache에서 EC2 자체 호스팅으로 전환했습니다. 

**왜 이런 결정을 했을까요?**
단순히 "직접 운영하는 게 편해서"가 아닙니다. 철저히 **비용 효율성** 관점에서의 접근이었습니다. 현재 회사가 보유한 Compute Savings Plan(SP)의 미소진분이 상당했는데, ElastiCache는 이 SP 커버 범위 밖입니다. 반면 EC2로 이전하면 컴퓨팅 비용은 SP로 흡수되고, EBS 실비만 지불하면 됩니다.

실측 결과, 월 $11.8 수준의 비용이 약 $0.73(EBS 비용)으로 줄어들었습니다. 작은 금액처럼 보일 수 있지만, 이런 최적화가 모여 전체 인프라 효율성을 결정합니다.

**기술적 포인트: 안전한 컷오버 전략**
갑작스러운 전환은 위험합니다. 그래서 저는 `redisMode`라는 4단계 분기 전략을 IaC(Infrastructure as Code)에 도입했습니다.

```typescript
// redisMode 분기 전략
// 'elasticache' → 현행 유지
// 'both'        → EC2를 띄우되 앱은 아직 관리형을 바라봄 (검증 단계)
// 'ec2'         → 앱이 EC2를 바라봄 (관리형은 롤백용으로 유지)
// 'ec2-only'    → 관리형 제거 (소킹 테스트 완료 후 최종 단계)
```

특히 이 Redis는 단순 캐시가 아니라 **Celery 브로커 및 결과 백엔드**로 사용됩니다. 큐 데이터 유실은 곧 태스크 유실을 의미하므로, `appendonly yes`와 `maxmemory-policy noeviction` 설정을 통해 데이터 영속성을 보장하는 데 집중했습니다.

### 2. "어느 서버에서 온 알림이지?" : 관찰 가능성(Observability) 개선

`metadium-explorer-stack` 작업에서는 운영 중 겪었던 아주 현실적인 문제를 해결했습니다. 텔레그램으로 알림을 받는데, 정작 어느 인스턴스에서 발생한 에러인지 구분할 수 없는 문제가 있었습니다.

기존에는 `[hostname | profile | instance]` 형태로 알림이 왔지만, Docker 환경에서는 `hostname`이 컨테이너 ID로 잡혀 매번 바뀌었고, `profile`은 상용과 개발 서버가 모두 `testnet`으로 동일했습니다. 결국 알림을 받고도 "어디를 확인해야 하지?"라는 의문이 생기는 상황이었습니다.

이를 해결하기 위해 두 가지 조치를 취했습니다.
1. **Docker Compose 수준에서 hostname 고정**: `dev189-api`, `dev189-sync-consumer` 등으로 명시하여 첫 번째 필드에서 즉시 식별 가능하게 했습니다.
2. **환경 변수를 통한 인스턴스 식별자 주입**: `SERVER_INSTANCE=189-testnet-dev`와 같은 고유 값을 주입하여 세 번째 필드에서도 명확히 구분되도록 했습니다.

단순한 설정 변경이지만, 장애 대응 시간을 단축시키는 결정적인 '운영의 묘'라고 생각합니다.

### 마치며: 엔지니어링의 본질은 '디테일'

오늘의 작업들을 관통하는 키워드는 **'디테일'**입니다. 비용을 줄이기 위해 SP 커버리지를 분석하고, 무중단 전환을 위해 4단계 컷오버 전략을 세우며, 알림 한 줄의 식별자를 고민하는 과정들이 결국 시스템의 안정성과 운영 효율을 만듭니다.

기술적 화려함보다 중요한 것은 **현재 우리 상황에 가장 적합한(Right-sized) 해결책을 찾아 실행하는 것**임을 다시 한번 느낀 하루였습니다.
