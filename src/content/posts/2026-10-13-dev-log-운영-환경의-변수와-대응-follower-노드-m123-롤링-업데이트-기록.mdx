# [Dev Log] 인프라의 디테일: 사내 Follower 노드 m1.2.3 업데이트와 예외 처리의 기록

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 20년 넘게 다양한 시스템을 다뤄왔지만, 여전히 가장 긴장되는 순간 중 하나는 운영 중인 노드의 바이너리를 교체하는 '롤링 업데이트' 작업입니다. 이론적으로는 단순한 프로세스 재시작이지만, 실제 운영 환경(Production)은 언제나 이론과 다른 변수들로 가득하기 때문입니다.

오늘은 사내 Follower 노드 5개 유닛을 대상으로 **m1.2.3 버전 선적용 작업**을 진행했습니다. 단순히 버전을 올리는 것을 넘어, 자동화 스크립트가 실제 환경의 '엣지 케이스'를 어떻게 만나고 어떻게 진화했는지에 대한 인사이트를 공유하고자 합니다.

---

### 1. 문제 정의와 기술적 결정

이번 작업의 핵심은 **"서비스 중단 최소화"**와 **"확실한 검증"**이었습니다. 이를 위해 다음과 같은 기술적 흐름을 설계했습니다.

- **사전 검증**: 업데이트 전 현재 블록 높이(head)와 공개 네트워크의 격차를 확인하여, 노드가 건강한 상태인지 먼저 체크합니다.
- **안전 장치**: 기존 systemd unit 파일을 `.bak` 형태로 백업하여 문제 발생 시 즉시 롤백할 수 있도록 했습니다.
- **사후 검증**: 재시작 후 `md5sum`을 통해 실제 실행 중인 바이너리가 새 버전인지 확인하고, `journalctl`을 통해 `SIGKILL`이나 `panic` 같은 치명적 오류가 없는지 스캔합니다.

### 2. 실전에서 만난 변수: "이론과 실제의 간극"

자동화 스크립트(`m123-roll-follower.sh`)를 실행하며 두 가지 흥미로운 예외 상황을 발견했습니다. 이것이 오늘 작업의 가장 큰 배움 포인트였습니다.

#### ① Unit 파일의 위치: `override.conf`의 존재
보통 서비스 설정은 `/etc/systemd/system/` 아래의 메인 파일에 있다고 생각합니다. 하지만 n183 노드에서는 `drop-in override.conf` 파일이 `ExecStart` 경로를 덮어쓰고 있었습니다. 기존 스크립트는 메인 파일만 수정했기에 업데이트가 반영되지 않는 문제가 발생했습니다.

이를 해결하기 위해 **"실제로 효력이 있는 마지막 파일"**을 찾는 로직으로 수정했습니다.
```bash
# 수정 전: UF=/etc/systemd/system/$U
# 수정 후: systemctl show를 통해 FragmentPath와 DropInPaths를 모두 탐색하여 실제 경로를 식별
UF=$(S "for f in \$(systemctl show $U -p FragmentPath --value) \$(systemctl show $U -p DropInPaths --value); do grep -q '^ExecStart=$OLDP' \$f 2>/dev/null && echo \$f; done | tail -1")
```

#### ② 서버 시간의 함정: UTC vs Local Time
로그를 분석할 때 `--since '$TS'`와 같이 절대 시각을 사용했는데, n183 서버의 시계가 UTC로 설정되어 있어 최근 로그가 조회되지 않는 현상이 있었습니다. 또한, `sudo` 권한 없이 `journalctl`을 호출하면 로그가 비어 있어 '오류 없음'으로 오판할 위험이 있었습니다.

결국 **상대 시간(`--since -10min`)**과 **명시적 `sudo -n`**을 사용하는 방식으로 변경하여 환경에 구애받지 않는 견고함을 확보했습니다.

### 3. 마치며: 엔지니어의 관점

이번 작업을 통해 다시 한번 느낀 점은, **최고의 자동화 도구는 '완벽한 설계'가 아니라 '실패를 통한 지속적인 보완'으로 완성된다**는 것입니다. 

`n183` 노드에서 발견한 `override.conf`나 시간대 설정 같은 디테일은 문서에 적혀 있지 않은 '살아있는 인프라'의 특성입니다. 이런 엣지 케이스를 하나씩 스크립트에 녹여낼 때, 비로소 우리는 "안전하게 자동화되었다"고 말할 수 있습니다.

씨피랩스에서도 이러한 기술적 집요함을 바탕으로 더 안정적인 Web3 인프라를 구축해 나가겠습니다.
