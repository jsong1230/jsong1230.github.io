안녕하세요, 시니어 소프트웨어 엔지니어이자 코드 리뷰어입니다.

오늘 제출하신 커밋들은 단순한 기능 구현을 넘어, **인프라 성능 최적화, 프레임워크의 동작 원리 분석을 통한 버그 수정, 그리고 매우 정교한 데이터 분석 기반의 콘텐츠 전략**까지 포함되어 있어 매우 인상적입니다. 특히 문제의 원인을 파악하기 위해 실측 데이터를 활용하고, 그 과정을 커밋 메시지에 상세히 기록하는 습관은 팀 전체의 기술 부채를 줄이는 훌륭한 태도입니다.

상세 리뷰를 작성해 드립니다.

## ✅ 잘한 점

### 1. 데이터 기반의 성능 최적화 및 과감한 단순화 (`heritageradio`)
- **근거:** `[landing] OG 이미지 동적 생성 제거` 커밋
- **리뷰:** ALB access log를 통해 `/opengraph-image` 요청이 전체의 69%를 차지하며 응답 시간이 1.9초에 달한다는 점을 정확히 짚어냈습니다. 동적 생성 결과와 정적 이미지의 차이가 없음에도 불필요하게 리소스를 소모하던 `ImageResponse` 로직을 제거하고 정적 파일(`.png`)로 전환함으로써, **응답 시간을 '즉시'로 단축하고 파일 크기를 84% 감소**시킨 결정은 매우 효율적인 최적화 사례입니다.

### 2. 프레임워크 내부 동작 원리 분석 및 명시적 해결 (`heritageradio`)
- **근거:** `[landing] fix: 랜딩 og:image 누락 복구` 커밋
- **리뷰:** Next.js의 `metadata` 상속 구조(Page의 `openGraph` 정의 시 Layout의 설정을 병합하지 않고 통째로 교체함)라는 함정을 정확히 찾아냈습니다. 특히 `opengraph-image.tsx`라는 파일 규약이 그동안 결함을 가려주고 있었다는 인과관계를 명확히 분석했습니다. 이를 단순히 수정하는 데 그치지 않고, **미래의 개발자가 같은 실수를 하지 않도록 `page.tsx`에 상세한 경고 주석(⚠️)을 남긴 점**이 매우 훌륭합니다.

### 3. 극한의 정밀도를 가진 데이터 스크리닝 (`booksummary`)
- **근거:** `docs: 고전소설 후보 2차 재공급` 커밋
- **리뷰:** 콘텐츠 선정 과정이 거의 '데이터 사이언스' 수준입니다. 단순히 수요가 많은 작품을 고르는 것이 아니라, `수요(네이버) $\to$ 경쟁(유튜브 제안어) $\to$ 의도(동음이의어 필터링)`라는 다단계 파이프라인을 구축하여 리스크를 최소화했습니다. 특히 '교과서 신호 $\neq$ 실제 수요'라는 가설을 데이터로 검증하고, '머리는 경쟁에, 꼬리는 수요에 막히는 구간'이라는 시장 분석 결과까지 도출한 점은 단순한 문서 작업을 넘어선 전략적 접근입니다.

- **리뷰:** Next.js의 특성상 `openGraph`를 정의하면 통째로 교체되기 때문에 현재처럼 명시적으로 적어주는 것이 정답입니다. 다만, `images`, `title`, `description` 등이 여러 페이지에서 반복될 가능성이 높다면, 이를 `metadata.ts` 같은 별도 설정 파일로 분리하여 **`const COMMON_OG_IMAGES = [...]` 형태로 상수로 관리**하고 가져다 쓰는 방식을 추천합니다. 현재는 주석으로 해결하셨지만, 프로젝트 규모가 커지면 오타로 인한 누락이 다시 발생할 수 있습니다.

## 💡 오늘의 기술 포인트

### 🚀 Next.js Metadata Overriding vs Merging
오늘 작업의 핵심 기술 포인트는 **Next.js App Router의 메타데이터 병합 전략**입니다. 
일반적인 설정값들은 상속(Merge)된다고 생각하기 쉽지만, `openGraph`나 `twitter` 같은 객체 타입의 메타데이터는 하위 페이지에서 정의하는 순간 상위 레이아웃의 해당 객체를 **완전히 덮어쓰기(Override)** 합니다. 

- **Lesson Learned:** "부분적 상속이 안 되는 필드가 있다면, 명시적으로 모든 필수 필드를 다시 정의하거나 상수를 통해 공유해야 한다."

또한, **동적 이미지 생성(`ImageResponse`) $\to$ 정적 자산(`public/og-image.png`)**으로의 전환은 "동적인 기능이 반드시 좋은 것은 아니며, 변화가 없는 데이터라면 정적 서빙이 압도적인 성능 우위를 가진다"는 기본 원칙을 다시 한번 확인시켜준 사례였습니다.
