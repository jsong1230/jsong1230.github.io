# [Dev Log] 인프라 보안 강화와 자동화된 대시보드 관리: 꼼꼼함이 만드는 안정성

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 20년 넘게 커리어를 쌓으며 느낀 점은, 거대한 아키텍처의 설계만큼이나 중요한 것이 바로 **'디테일한 운영의 완결성'**이라는 것입니다. 특히 블록체인 노드나 API 게이트웨이처럼 외부 노출이 잦은 인프라에서는 작은 설정 하나가 보안 홀이 될 수 있고, 반대로 작은 기록의 누락이 나중에 큰 추적 비용으로 돌아오곤 합니다.

오늘은 인프라 보안 필터 최적화 작업과 개인 개발 대시보드 업데이트 내용을 정리해 보려 합니다.

---

### 1. Nginx 필터 최적화: "불필요한 예외는 잠재적 위험이다"

오늘 가장 핵심적인 작업은 `api1`, `api2` 서버의 Nginx 필터에서 특정 IP(`34.198.53.234`)에 부여되었던 허용 예외를 제거하는 것이었습니다.

**문제 상황과 결정:**
기존에는 특정 목적을 위해 `debug` 메서드 등에 접근할 수 있는 예외 IP가 설정되어 있었습니다. 하지만 내부 조사 결과, 해당 IP는 우리 AWS 자산이 아니며 거래소에 제공한 이력도 없다는 것이 확인되었습니다. "Open API에서 debug 권한은 불필요하다"는 명확한 판단 하에 모든 공용 디버그 접근을 차단하기로 결정했습니다.

**기술적 접근과 배운 점:**
단순히 설정 파일을 수정하고 리로드하는 것에 그치지 않고, **'검증의 루프'**를 설계했습니다.

```text
검증: 두 노드: 정상 200 · debug 403 · ★XFF 34.198.53.234 → 403 · 배치 403
```

위의 로그처럼, 정상 요청은 200 OK가 나오는지, 차단되어야 할 디버그 요청과 XFF(X-Forwarded-For)를 통한 우회 시도가 정확히 403 Forbidden으로 떨어지는지 전수 검사했습니다. 

재미있었던 점은 집행 과정에서 `grep` 리터럴 처리 문제로 첫 시도에 변경 사항이 반영되지 않았던 찰나의 실수였습니다. 이를 통해 다시 한번 쉘 스크립트에서 특수문자 처리(`-F` 옵션 사용 등)의 중요성을 상기했습니다. 인프라 작업에서는 **'당연히 되겠지'라는 생각보다 '어떻게 실패할 수 있는가'를 고민하는 태도**가 사고를 막는 유일한 길입니다.

### 2. 데이터 기반의 자기 객관화: Dashboard 업데이트

개인 프로젝트들의 활동량을 추적하는 `dashboard.json` 데이터도 업데이트했습니다. 

```json
- "commits_7d": 49,
- "commits_30d": 155
+ "commits_7d": 59,
+ "commits_30d": 407
```

단순한 숫자 변경처럼 보이지만, 저는 이 데이터를 통해 제가 현재 어떤 기술 스택에 몰입하고 있는지, 그리고 리소스 배분이 효율적인지를 모니터링합니다. 최근 `claude-agent` 관련 커밋 수가 급증한 것을 보며, AI 에이전트를 활용한 워크플로우 자동화가 제 생산성 모델의 중심축으로 이동하고 있음을 정량적으로 확인할 수 있었습니다.

### 3. 마무리하며: 기록이 곧 자산이다

오늘의 작업 로그를 보면 `docs(log)`라는 커밋 메시지가 굉장히 많습니다. 누군가는 "코드 짜기도 바쁜데 로그를 이렇게까지 상세히 남겨야 하나?"라고 물을 수 있습니다. 

하지만 씨피랩스에서 수많은 복잡한 시스템을 운영하며 깨달은 것은, **잘 작성된 로그는 미래의 나에게 주는 가장 친절한 가이드북**이라는 점입니다. 특히 주말 등록 규약 변경 같은 정책적인 결정 사항을 `MEMORY.md`와 전역 설정 파일에 전파하고 기록하는 과정은, 협업 시 커뮤니케이션 비용을 획기적으로 줄여줍니다.

기술적 깊이는 코드에서 나오지만, 시스템의 안정성은 그 코드를 둘러싼 꼼꼼한 기록과 검증에서 완성됩니다. 오늘도 '완결성' 있는 하루를 보냈다는 만족감으로 로그를 마칩니다.
