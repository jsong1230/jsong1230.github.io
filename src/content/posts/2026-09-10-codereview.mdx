안녕하세요, 시니어 소프트웨어 엔지니어이자 코드 리뷰어입니다.

오늘 제출하신 커밋은 단순한 코드 변경을 넘어, **운영 환경의 가시성(Observability) 확보와 효율적인 리소스 관리**라는 관점에서 매우 훌륭한 접근을 보여주고 있습니다. 특히 배포 문서(`PROD-DEPLOY.md`)에 기록된 분석 과정과 검증 논리가 매우 인상적입니다.

상세 리뷰 결과입니다.

---

## ✅ 잘한 점

1. **데이터 기반의 문제 정의 및 원인 분석**
   - 단순히 "로그가 많다"가 아니라, `하루 ~19,000줄`, `GET /api/int/v1/transactions/null 5,436건/일`과 같이 정확한 수치와 요청 경로, 요청자 IP(`57.141.2.0/24`)를 분석하여 문제의 원인이 외부 크롤러임을 명확히 규명했습니다. 이는 시니어 엔지니어가 가져야 할 가장 핵심적인 역량입니다.

2. **다층 방어 전략 (Multi-layered Defense) 적용**
   - 문제를 해결하기 위해 한 곳만 수정하지 않고, **Frontend(사전 필터링) $\rightarrow$ Backend(로그 레벨 조정) $\rightarrow$ Nginx(가드)**로 이어지는 계층적 대응을 설계했습니다. 특히 프론트엔드에서 `utils/identifier.js`를 통해 API 호출 자체를 차단하여 서버 리소스 낭비를 원천 봉쇄한 결정이 매우 효율적입니다.

3. **엄격하고 논리적인 검증 방법론**
   - "404 응답이 오니 성공이다"라는 일반적인 착각을 경계하고, **"API 실패로도 404가 날 수 있다"**는 점을 지적하며 Nginx 접근 로그의 요청 수를 직접 카운트하는 방식을 택했습니다. 이는 엣지 케이스를 고려한 매우 정교한 검증 방식입니다.

4. **상세한 배포 및 롤백 가이드 기록**
   - `PROD-DEPLOY.md`에 배포 시간, 적용 PR 번호, 구체적인 검증 결과뿐만 아니라 **롤백 방법(이미지 태그 및 명령어)**까지 명시하여, 장애 발생 시 대응 시간을 최소화할 수 있도록 문서화했습니다.

## 🔧 개선할 점

1. **로그 레벨 전략의 표준화**
   - 현재 4xx 에러를 `log.warn`으로 변경하셨는데, 이는 소음 제거에는 효과적이지만 모니터링 시스템(예: ELK, Sentry)에서 '경고' 알람이 너무 많이 발생할 가능성이 있습니다. 
   - **제안:** 특정 패턴(예: `/null` 요청)의 4xx 에러는 `DEBUG` 레벨로 내리거나, 아예 로그에서 제외하는 `Filter`를 Logback 설정에 추가하여 `WARN` 레벨의 순수성을 유지하는 것을 권장합니다.

2. **하드코딩된 가드 로직의 관리**
   - 프론트엔드 `utils/identifier.js`에서 모양을 보고 API 호출을 막는 로직이 추가되었습니다. 만약 크롤러의 패턴이 변경되거나, 정당한 요청이 해당 패턴에 걸릴 경우 대응이 늦어질 수 있습니다.
   - **제안:** 이러한 '차단 패턴'들을 설정 파일이나 DB로 관리하여, 코드 배포 없이도 패턴을 업데이트할 수 있는 구조를 고민해보시면 좋을 것 같습니다.

## 💡 오늘의 기술 포인트

**"가짜 API(Mock)를 활용한 로컬 검증 환경 구축"**
- 배포 전 `156` 서버에서 이미지를 띄우고 `host.docker.internal`을 가짜 API로 연결해 요청 수를 센 과정이 매우 훌륭합니다. 상용 환경에 영향을 주지 않고 실제 트래픽 흐름을 시뮬레이션하여 가설을 검증한 이 패턴은, 위험도가 높은 인프라 변경 작업 시 반드시 적용해야 할 **Best Practice**입니다.

**총평:** 
단순한 버그 수정이 아니라 **분석 $\rightarrow$ 가설 $\rightarrow$ 검증 $\rightarrow$ 적용 $\rightarrow$ 문서화**의 전체 사이클을 완벽하게 수행한 작업입니다. 특히 운영 환경의 로그 소음을 줄여 실제 중요한 ERROR 로그에 집중할 수 있게 만든 점은 시스템의 안정성을 크게 높이는 기여입니다. 고생하셨습니다!
