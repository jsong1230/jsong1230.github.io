# [Dev Log] 데이터 기반의 가시성 확보와 인프라 모니터링의 디테일

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey)입니다.

엔지니어로서 20년 넘게 커리어를 쌓으며 깨달은 점 중 하나는, 결국 **'측정할 수 없는 것은 관리할 수 없다'**는 것입니다. 이는 거대한 분산 시스템의 아키텍처 설계뿐만 아니라, 개인의 생산성 관리나 일일 인프라 상태 체크 같은 아주 작은 단위의 작업에서도 동일하게 적용됩니다.

오늘은 제가 개인적으로 운영하는 대시보드 데이터 업데이트와 씨피랩스 인프라의 상태 점검 작업을 진행했습니다. 단순한 '업데이트'와 '체크'처럼 보이지만, 그 이면의 기술적 의도와 인사이트를 공유해보고자 합니다.

### 1. 데이터 기반의 자기 객관화: Dashboard 업데이트

먼저 제 개인 GitHub 페이지(`jsong1230.github.io`)의 대시보드 데이터를 갱신했습니다. 저는 제가 어떤 프로젝트에 얼마나 시간을 쏟고 있는지, 커밋 빈도는 어떻게 변하는지를 JSON 형태로 관리하여 시각화하고 있습니다.

이번 변경 사항에서 흥미로운 점은 `claude-agent` 리포지토리의 활동량 변화입니다.

```json
{
  "name": "claude-agent",
  "last_date": "2026-11-17",
  "last_msg": "log: briefick 11/16 registered on request...",
  "commits_7d": 38,
  "commits_30d": 403
}
```

최근 30일간 400개가 넘는 커밋이 발생한 것을 볼 수 있습니다. 단순히 양적인 팽창이 아니라, AI 에이전트를 활용한 로그 자동화와 관리 체계를 구축하며 발생하는 '반복적 최적화'의 결과입니다. 이렇게 데이터를 수치화해두면, 내가 현재 어떤 기술적 도전에 몰입하고 있는지, 혹은 어느 부분에서 병목이 생겨 활동이 뜸해졌는지를 객관적으로 파악할 수 있습니다.

### 2. 인프라 모니터링: '정상'이라는 확신을 갖는 법

이어 씨피랩스의 메인넷 노드와 Zabbix 모니터링 서버의 상태를 점검했습니다. 인프라 엔지니어에게 가장 고통스러운 순간은 "문제가 있는데 모를 때"가 아니라, **"문제가 없는 것 같은데 확신이 없을 때"**입니다.

오늘 로그에서 주목할 부분은 `binlog trim` 이후의 디스크 사용량 관리입니다.

> `- Zabbix 서버 루트: CPLABS 51.06% · Metadium 31.44% (11/16 binlog 정리 뒤 유지)`

데이터베이스의 binlog가 쌓이면 디스크 풀(Full) 장애로 이어져 서비스 전체가 중단될 수 있습니다. 이를 사전에 정리하고, 정리 후의 수치가 안정적으로 유지되는지를 확인하는 과정은 매우 기본적이지만 치명적인 장애를 막는 핵심 루틴입니다.

또한, 1분 내외로 짧게 발생했다 사라진 부하 경보(Load Alert)에 대해서도 기록을 남겼습니다. 당장 해결된 문제라 하더라도, 이러한 '찰나의 이상 징후'들이 모여 패턴을 형성하고, 그것이 곧 잠재적인 아키텍처 결함을 찾아내는 단서가 되기 때문입니다.

### 마치며: 기록이 곧 기술력이다

오늘의 작업은 화려한 신기술 도입이나 복잡한 알고리즘 구현은 아니었습니다. 하지만 **데이터를 최신화하고, 시스템의 상태를 꼼꼼히 기록하는 행위** 자체가 엔지니어링의 본질이라고 생각합니다.

로그 하나, JSON 수치 하나를 정교하게 관리하는 습관이 결국 대규모 시스템의 안정성을 결정짓습니다. 씨피랩스에서도 이러한 '디테일의 힘'을 바탕으로 더 견고한 Web3 인프라를 만들어가겠습니다.

**Jeffrey's Insight:**
*   **가시성(Visibility):** 보이지 않는 것은 관리할 수 없다. 나 자신의 생산성부터 서버의 디스크 잔량까지 모두 수치화하라.
*   **기록의 가치:** "잠깐 발생했다가 사라진 에러"를 무시하지 마라. 그것이 다음번 대형 장애를 막을 유일한 힌트일 수 있다.
