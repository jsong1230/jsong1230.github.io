# [Dev Log] 로그 소음 제거: "404가 나온다"는 것만으로 충분하지 않은 이유

안녕하세요, 씨피랩스(CP Labs)의 송주한입니다.

엔지니어로서 시스템을 운영하다 보면, 어느 날 갑자기 로그 파일의 크기가 비정상적으로 커지거나 ERROR 레벨의 로그가 쏟아지는 상황을 마주하곤 합니다. 대부분의 경우 이는 시스템의 치명적인 결함보다는, 외부의 예측하지 못한 요청(Unexpected Request)이 내부의 예외 처리 로직과 만나 발생하는 '로그 소음(Log Noise)'인 경우가 많습니다.

오늘 제가 해결한 작업이 바로 이 지점이었습니다.

### 1. 문제의 발견: 하루 19,000줄의 ERROR 로그
상용 API 서버의 로그를 모니터링하던 중, 하루에 약 19,000줄에 달하는 ERROR 로그가 쌓이고 있는 것을 발견했습니다. 분석 결과, 대부분이 클라이언트 측의 잘못된 요청(4xx)이었으며, 특히 특정 패턴의 요청이 반복되고 있었습니다.

```text
GET /api/int/v1/transactions/null   5,436건/일
GET /api/int/v1/blocks/null         4,102건/일
출처: meta-externalagent (Meta 크롤러)
```

알고 보니 Meta의 크롤러가 `/tx/null`이나 `/block/null` 같은 잘못된 경로를 지속적으로 긁어 가고 있었고, 이것이 서버의 `GlobalExceptionHandler`를 거치며 매 요청당 2줄의 ERROR 로그를 남기고 있었습니다. 시스템에 실질적인 장애는 없었지만, 정작 중요한 진짜 에러를 놓치게 만드는 전형적인 '소음'이었죠.

### 2. 기술적 결정: 이중 가드(Double Guard) 전략
단순히 로그 레벨만 낮추는 것이 아니라, 불필요한 요청이 서버 리소스를 낭비하지 않도록 프론트엔드와 백엔드 양측에서 대응하는 전략을 세웠습니다.

*   **Frontend (PR #103):** `utils/identifier.js`를 통해 요청 값의 형식을 먼저 검증합니다. 값이 `null`이거나 형식이 맞지 않으면 **애초에 API를 호출하지 않고** 404 처리를 하여 네트워크 비용을 줄였습니다.
*   **Backend (PR #55):** 
    *   4xx 응답은 `log.error`가 아닌 `log.warn`으로 변경하여 알람 소음을 제거했습니다. (단, 5xx 및 텔레그램 알림 경로는 유지)
    *   중복으로 기록되던 검증기 로그 레벨을 `log.debug`로 낮춰 로그의 밀도를 최적화했습니다.

### 3. 인사이트: 검증의 정밀함에 대하여
이번 작업에서 가장 중요하게 생각한 점은 **"어떻게 이 가드가 실제로 동작하는지 증명할 것인가"**였습니다.

많은 개발자가 "브라우저에서 404가 뜨니 잘 동작한다"라고 생각하고 넘어갑니다. 하지만 저는 여기서 한 단계 더 들어갔습니다. API 서버 내부의 오류로 인해 404가 발생할 수도 있기 때문에, 단순히 응답 코드만으로는 가드(Guard)의 동작 여부를 확신할 수 없습니다.

> **"404가 나온다"만으로는 가드 동작을 알 수 없다.**
> nginx 접근 로그에서 **api로 나간 요청 수를 직접 세는 것**이 유일하게 맞는 검증이다.

실제로 배포 후, 잘못된 요청을 보냈을 때 nginx 로그에서 API 컨테이너로 전달된 요청 수가 `0건`임을 확인하고, 정상적인 해시 요청 시에만 `1건`이 전달되는 것을 실측함으로써 가드가 정확히 작동함을 검증했습니다.

### 마치며
로그는 시스템의 상태를 알려주는 소중한 지표이지만, 관리되지 않는 로그는 오히려 독이 됩니다. 특히 대규모 트래픽을 처리하는 환경일수록 '정확한 로그 레벨 설정'과 '불필요한 요청의 조기 차단'은 시스템 안정성의 핵심입니다.

단순한 코드 수정보다 더 중요한 것은, 내가 수정한 코드가 의도대로 동작한다는 것을 **어떤 지표로 증명할 것인가**에 대한 고민이라는 점을 다시 한번 느낀 하루였습니다.
