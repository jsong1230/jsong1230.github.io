# 인프라 최적화와 장애 대응: ALB 통합과 런타임 패닉 해결 기록

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어에게 가장 보람찬 순간 중 하나는 복잡하게 얽혀 있던 인프라를 단순화하고, 원인을 알 수 없던 시스템의 '비명(Panic)'을 정확히 진단해냈을 때가 아닐까 합니다. 오늘은 제가 진행한 인프라 효율화 작업과 런타임 에러 분석 과정을 공유해 보려 합니다.

### 1. 인프라 다이어트: ALB 통합을 통한 비용 및 관리 효율화

최근 씨피랩스에서는 흩어져 있던 Application Load Balancer(ALB)를 하나로 통합하는 작업을 진행하고 있습니다. 오늘은 그 세 번째 단계로 메인넷 익스플로러(Mainnet Explorer)의 웹 트래픽을 API 허브로 이관하는 작업을 완료했습니다.

단순히 옮기는 것보다 중요한 것은 **'기존 규칙과의 충돌을 어떻게 피하느냐'**였습니다. 특히 API 허브에는 모든 호스트의 `/api/v1/*` 경로를 특정 서비스로 보내는 우선순위가 낮은(p100) 규칙이 이미 존재했습니다. 자칫하면 새로운 트래픽이 이 규칙에 '납치'될 위험이 있었죠.

여기서 제가 선택한 기술적 결정은 **우선순위의 전략적 배치**였습니다.

> **"front/ws host 규칙을 p10·p20(p100보다 앞)에 배치해 기존 규칙 무수정으로 해소"**

기존의 광범위한 규칙을 수정하다가 다른 서비스에 영향을 주는 리스크를 감수하기보다, 더 구체적인 호스트 규칙을 상단에 배치함으로써 안전하게 트래픽을 분리했습니다. 결과적으로 7개의 구형 ALB를 삭제 대기 상태로 만들었고, 월 약 $154의 비용을 절감함과 동시에 관리 포인트를 획기적으로 줄였습니다.

### 2. 런타임 패닉 분석: `unwrap`의 위험성과 외부 의존성

인프라 작업 외에도 Bifrost 릴레이어(Relayer)에서 발생한 크래시 루프(Crash Loop)를 분석했습니다. 워치독 경보를 통해 확인한 결과, 약 90분 동안 83번의 패닉이 발생했더군요.

로그를 추적해 보니 원인은 명확했습니다. 비트코인 프로바이더(dRPC)가 `getblockcount` 요청에 대해 일시적으로 `null`을 반환했고, 이를 처리하는 벤더 코드에서 **`.unwrap()`**을 사용해 강제로 값을 꺼내려다 패닉이 발생한 것입니다.

```rust
// 분석된 문제 지점: btc/block.rs:84
// 프로바이더의 null 응답 -> unwrap() 호출 -> Panic 발생
```

러스트(Rust)에서 `unwrap()`은 "이 값은 절대 null일 리 없다"는 개발자의 강한 확신을 의미하지만, 외부 API와 통신하는 분산 시스템 환경에서 이러한 확신은 매우 위험합니다. 이번 사례는 외부 의존성(External Dependency)이 언제든 예기치 못한 응답을 보낼 수 있음을 다시 한번 상기시켜 주었습니다.

다행히 시스템은 자연 회복되었고, 장애 재발 시 즉시 교체할 수 있는 예비 프로바이더(publicnode)까지 검증을 마쳤습니다. 해당 내용은 벤더 측에 제2의 패닉 지점으로 리포트하여 패치를 요청할 예정입니다.

### 마치며: 엔지니어의 관점

오늘의 작업들을 통해 느낀 점은 **'단순함이 곧 안정성'**이라는 것입니다. ALB를 통합해 복잡도를 낮추는 것과, 코드 수준에서 예외 처리를 꼼꼼히 하여 런타임의 불확실성을 제거하는 것은 결국 같은 방향을 향하고 있습니다.

인프라의 비용을 줄이는 것도 중요하지만, 그 과정에서 기존 시스템의 미스라우팅(Misrouting)을 발견하고 바로잡는 '부수적인 이득'을 얻었을 때 엔지니어로서 큰 희열을 느낍니다. 앞으로도 씨피랩스의 시스템을 더 단단하고 효율적으로 만들어 나가겠습니다.
