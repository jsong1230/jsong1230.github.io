# [Engineering Log] 찰나의 실수와 기록의 힘: 인프라 마이그레이션 중 마주한 '거짓 성공'과 '순서의 함정'

안녕하세요, 씨피랩스(CP Labs)의 송주한입니다.

엔지니어로서 20년 넘게 다양한 시스템을 다뤄왔지만, 대규모 데이터가 얽힌 인프라 마이그레이션은 언제나 긴장의 연속입니다. 특히 수백 GB, 수 TB 단위의 데이터를 옮기는 작업에서는 '작은 절차의 차이'가 수십 분의 시간 낭비나, 최악의 경우 데이터 손실로 이어지기 때문입니다.

오늘은 제가 진행한 API 노드 타입 전환 및 데이터 마이그레이션 과정에서 겪은 기술적 시행착오와 그 해결 과정을 공유해보려 합니다.

### 1. '거짓 성공(False Success)'의 무서움

오늘 작업 중 가장 아찔했던 순간은 `phaseA` 단계에서 발생했습니다. 스크립트는 `PHASEA_DONE`이라는 성공 메시지를 띄웠지만, 실제로는 **부팅이 불가능한 디스크**가 만들어진 상태였습니다.

원인은 `sgdisk`의 기본 섹터 정렬(2048-sector alignment) 문제로 인해 BIOS 부트 파티션 생성에 실패했고, 결과적으로 `grub-install`이 실행되지 않은 것이었습니다. 더 큰 문제는 제 스크립트가 `grub-install`의 리턴 코드를 엄격하게 체크하지 않았고, 기존 루트에서 복사된 `core.img` 파일을 보고 "파일이 존재하니 성공했다"라고 판단했다는 점입니다.

**인사이트:** 
로그에 찍힌 "Success"라는 글자보다 중요한 것은 **'실제 동작하는가'에 대한 실증(Verification)**입니다. 결국 저는 버려지는 `t3.small` 인스턴스에 해당 볼륨을 붙여 직접 부팅 테스트를 진행함으로써 이 문제를 잡아낼 수 있었습니다. 자동화 도구가 주는 안도감보다, 결정적인 순간의 수동 검증(Manual Sanity Check)이 왜 필요한지를 다시금 깨달았습니다.

### 2. 인스턴스 스토어와 '순서의 함정'

두 번째 문제는 `api2` 노드의 스왑 절차에서 발생했습니다. 작성된 절차서는 다음과 같았습니다.
`벌크 복사` $\rightarrow$ `인스턴스 정지(Stop)` $\rightarrow$ `루트 스왑` $\rightarrow$ `시작`

하지만 여기서 치명적인 간과가 있었습니다. AWS의 **인스턴스 스토어(Instance Store)는 인스턴스를 정지(Stop)하는 순간 데이터가 소멸**한다는 점입니다. 즉, 열심히 복사한 수백 GB의 데이터가 스왑 직전에 모두 사라지는 구조였습니다.

다행히 과거의 기록(ARCHIVE2 BLOCKER 문서)에서 "스톱이 복사보다 앞서야 한다"는 답을 찾아내어 즉시 교정했습니다.
- **교정된 순서:** `정지` $\rightarrow$ `타입 변경/스왑` $\rightarrow$ `부팅` $\rightarrow$ `바인드 마운트` $\rightarrow$ `복사`

```text
- 손실: 진행 중이던 복사 33G/4분을 폐기. 그대로 뒀으면 30분 더 쓰고 전부 잃을 뻔했다.
```
위의 로그처럼, 빠르게 오류를 인지하고 4분의 작업을 버린 덕분에 30분 이상의 시간 낭비를 막을 수 있었습니다.

### 3. 의존성 해결: 고립된 노드를 구하라

마지막으로 기술적 결정이 필요했던 부분은 피어(Peer) 의존성 문제였습니다. `api2` 노드가 `api1` 하나에만 의존해 부트스트래핑을 하고 있었는데, 만약 `api1`을 점검을 위해 내리면 `api2`는 즉시 고립되어 트래픽을 처리할 수 없는 상태가 됩니다.

이를 해결하기 위해 `static-nodes.json` 배포 시점을 앞당겨 `api1`, `pn1`, `pn3`를 모두 포함하도록 설정했고, `admin.addPeer`를 통해 재시작 없이 실시간으로 피어를 확장하여 안정적인 네트워크 톱폴로지를 확보했습니다.

### 마치며

오늘의 작업은 단순히 서버 사양을 올리는 일이 아니었습니다. **"기록된 절차가 항상 정답은 아니며, 실행 결과에 대한 끊임없는 의심과 검증이 시스템의 안정성을 만든다"**는 기본 원칙을 다시 확인하는 과정이었습니다.

씨피랩스에서 다루는 Web3 인프라는 24시간 중단 없이 돌아가야 하기에, 이러한 디테일한 검증 과정이 곧 서비스의 신뢰도로 이어진다고 믿습니다. 오늘도 기록하고, 의심하고, 검증하며 한 걸음 더 성장합니다.
