# [Dev Log] 시스템의 '사각지대'를 찾아내는 법: TTS 최적화부터 거버넌스 도구 설계까지

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 가장 경계해야 할 것은 "당연히 이렇겠지"라는 가설입니다. 특히 복잡한 분산 시스템이나 레거시가 섞인 환경에서는 가설과 실제의 괴리가 곧 장애나 데이터 유실로 이어지곤 합니다. 오늘 저는 두 가지 서로 다른 프로젝트를 통해, 시스템의 '사각지대'를 어떻게 실증하고 메우는지에 대한 인사이트를 얻었습니다.

---

### 1. Heritage Radio: 로그의 함정과 자원 분리의 실측

최근 진행 중인 TTS(Text-to-Speech) 콘텐츠 생성과 빌드 작업에서 흥미로운 지점이 있었습니다. 

**문제는 '슬롯 초과 경고'의 가시성이었습니다.** 
사전에 경고 로직을 구현했지만, 정작 빌드 드라이버나 cron 로그에는 아무런 기록이 남지 않았습니다. 자칫하면 "경고 로직이 동작하지 않는다"고 오진할 뻔했으나, 실제 데이터 흐름을 추적한 결과 경고는 Celery 워커의 컨테이너 로그(`docker logs grnal-celery-worker-build`)에만 남고 있었습니다.

```bash
# 드라이버 로그 grep 0건 vs docker logs 44건 실측
# 🚨 경고는 cron 로그가 아니라 celery-worker 로그에만 남는다.
```

이 과정에서 **자원 분리의 효율성**도 확인했습니다. TTS 작업(GPU 중심)과 사이클 빌드(CPU 중심)를 병행했음에도 불구하고, 큐와 자원을 분리한 덕분에 빌드 소요 시간이 단독 실행 시와 동일한 49~50분을 유지했습니다. 이론적인 설계가 실제 실측 데이터로 증명될 때의 쾌감이 바로 엔지니어링의 묘미가 아닐까 합니다.

### 2. Web3 거버넌스: 테스트넷의 함정과 '가드레일' 설계

또 다른 작업인 메인넷 거버넌스 도구 개발에서는 더 위험한 '가설의 오류'를 발견했습니다. 

기존에는 메인넷의 특정 노드(meta3)가 제안서를 제출하면 투표 없이 즉시 적용될 것이라 생각했습니다. 하지만 이는 **테스트넷의 구조(Staker=Voter 통합)를 메인넷에 잘못 투영한 결과**였습니다. 메인넷은 Staker와 Voter가 분리되어 있어 반드시 과반(5/9)의 투표 경로를 거쳐야만 했습니다.

이 '공백'을 메우기 위해 급히 `gov-vote-calldata.py`라는 투표 전용 도구를 신설했습니다. 특히 거버넌스 트랜잭션은 한 번의 실수가 치명적이기에, 단순 전송이 아닌 **3단계 가드레일**을 설계했습니다.

1. **Ballot 대조**: `getBallotInVoting()`을 통해 현재 진행 중인 투표 번호가 맞는지 자동 확인 (오투표 방지)
2. **멤버 검증**: 투표자가 실제 권한을 가진 멤버인지 확인
3. **라운드트립 검산**: 생성된 Calldata를 다시 디코딩하여 의도한 값과 일치하는지 검증

### 마치며: 엔지니어의 자세

오늘의 작업들을 관통하는 핵심은 **"실증(Verification)"**입니다. 
- 로그가 안 찍힌다면 로그의 위치를 의심하고, 
- 시스템 동작이 예상과 다르다면 환경(Testnet vs Mainnet)의 차이를 분석하며, 
- 치명적인 작업일수록 도구 자체에 '가드레일'을 심어 인간의 실수를 시스템적으로 차단하는 것.

20년 넘게 엔지니어로 일하며 깨달은 점은, 가장 완벽한 코드는 '완벽하게 짠 코드'가 아니라 '어디가 틀렸는지 빠르게 찾아낼 수 있게 설계된 코드'라는 점입니다. 내일은 오늘 설계한 런북을 바탕으로 리허설을 통해 마지막 미결 사항들을 확인해 볼 예정입니다.
