# [Dev Log] 보이지 않는 결함을 찾는 법: 자동화 백업의 함정과 무결성 검증

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서 가장 경계해야 할 순간은 "로그상으로는 성공(Success)인데, 실제 결과물은 틀렸을 때"입니다. 시스템이 '정상'이라고 외치고 있지만, 실제 데이터는 오염되어 있는 상태. 이 간극을 메우는 것이 바로 시니어 엔지니어가 해야 할 '근본적인 문제 해결(Root-cause Fix)'의 핵심입니다.

오늘은 제가 씨피랩스에서 진행한 인프라 백업 자동화 수정 작업과 개인 프로젝트에서 겪은 렌더링 사고를 통해, **'실패를 어떻게 정의하고 검증할 것인가'**에 대해 이야기해보려 합니다.

---

### 1. "조용한 실패(Silent Failure)"와의 싸움: 백업 스크립트 교정

최근 `fn2` 노드의 백업 크론잡(cron job)을 구축했습니다. 로그상으로는 4시간 45분 동안 267GB의 데이터를 S3로 성공적으로 스트리밍했고, 프로세스도 정상 종료되었습니다. 하지만 실제 게시된 MD5 해시값을 확인해보니 2주 전의 '스테일(stale)'한 값이 그대로 올라가 있었습니다.

**문제의 원인은 아주 사소하지만 치명적인 '권한' 문제였습니다.**
`/tmp/backup_md5` 파일이 과거 root 권한으로 실행되었을 때 생성되었고, 이후 ubuntu 계정으로 실행된 스크립트가 이 파일에 쓰기를 시도했지만 `sticky bit` 설정 등으로 인해 쓰기가 조용히 실패(silent failure)한 것입니다. 쉘 스크립트 특성상 파이프라인의 일부 실패가 전체 프로세스의 종료 코드를 바꾸지 않았기에, 시스템은 이를 '성공'으로 판정했습니다.

**기술적 결정: Fail-Closed 전략 도입**
단순히 권한을 수정하는 것에 그치지 않고, 구조적인 안전장치를 추가했습니다.

*   **경로 변경 및 원자적 쓰기**: `/tmp`가 아닌 `/opt/meta/` 하위의 전용 경로를 사용하고, `tmp + mv` 방식을 통해 쓰기 도중 파일이 깨지는 것을 방지했습니다.
*   **Fail-Closed 구현**: MD5 생성에 실패할 경우, 이전 값을 그대로 사용하는 것이 아니라 `FILE_MD5="unavailable"`로 처리하여 관리자가 즉시 문제를 인지하게 했습니다.

```bash
# 수정 방향: 스테일 값 게시를 원천 차단하고 실패 시 명시적 경고
# [기존] tee >(md5sum > /tmp/backup_md5) -> 쓰기 실패해도 프로세스 지속
# [수정] /opt/meta/backup_md5 사용 + 실패 시 "unavailable" 처리
```

또한, S3 라이프사이클(9일)과 맞지 않았던 기존의 '7일 전 날짜 매칭 삭제' 로직을 `keep-last-2`(최신 2개 유지) 방식으로 변경하여 데이터 정합성을 맞췄습니다.

### 2. 병렬 처리의 함정: 중복 렌더링 사고

개인 프로젝트인 `booksummary` 작업 중에도 비슷한 교훈을 얻었습니다. GPU 렌더링 스크립트(`create_full_episode.py`)를 실수로 두 번 실행했는데, 두 프로세스가 동일한 출력 파일에 동시에 쓰기를 시도하면서 파일이 심각하게 손상되었습니다.

결과물에는 22만 건이 넘는 NAL unit 에러가 발생했고, 프레임 seek가 불가능한 상태가 되었습니다. 겉보기엔 파일 용량이 정상이었기에, 직접 무결성 검사를 하기 전까지는 알 수 없었던 사고였습니다.

**배운 점: 검증 절차의 공식화**
이번 사고를 통해 렌더링 파이프라인에 두 가지 필수 절차를 추가했습니다.
1. **Pre-check**: `pgrep -f`를 통해 동일 프로세스가 실행 중인지 확인.
2. **Post-check**: `ffmpeg -v error -i <file> -f null -` 명령어를 통해 스트림 무결성을 최종 검증한 후 업로드 단계로 진입.

### 마치며: 엔지니어의 인사이트

오늘의 작업들을 관통하는 하나의 키워드는 **'명시적 검증'**입니다.

- "로그에 Success가 떴으니 됐겠지" $\rightarrow$ **위험한 생각입니다.**
- "파일 용량이 맞으니 정상겠지" $\rightarrow$ **착각입니다.**

진정한 자동화는 단순히 '돌아가는 것'이 아니라, **'어디서 어떻게 틀렸는지를 정확히 알려주는 것'**에서 완성됩니다. 특히 Web3나 블록체인 인프라처럼 데이터의 무결성이 생명인 분야에서는 이러한 'Fail-Closed' 설계와 '끝단 검증(End-to-End Verification)' 습관이 시스템의 신뢰도를 결정짓습니다.
