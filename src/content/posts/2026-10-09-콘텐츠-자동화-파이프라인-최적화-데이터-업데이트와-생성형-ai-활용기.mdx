# [Dev Log] 데이터의 정교함과 생성형 AI의 한계를 다루는 법: 콘텐츠 자동화 파이프라인 최적화

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어로서의 삶은 단순히 코드를 짜는 것에 그치지 않고, 내가 가진 기술적 도구들을 활용해 일상의 생산성을 극대화하는 과정의 연속인 것 같습니다. 오늘은 개인 프로젝트인 콘텐츠 자동화 파이프라인의 데이터 업데이트와, 생성형 AI(Flux)를 활용한 이미지 생성 과정에서 겪은 시행착오와 해결 방법을 공유해 보려 합니다.

## 1. 대시보드 데이터 업데이트: 나의 '디지털 발자국' 기록하기

먼저 진행한 작업은 개인 대시보드(`dashboard.json`)의 데이터를 최신화하는 것이었습니다. 저는 제가 운영하는 여러 저장소의 활동량과 커밋 로그를 시각화하여 관리하고 있습니다. 

이번 업데이트에서 흥미로운 점은 `claude-agent` 저장소의 폭발적인 활동량입니다. 7일간의 커밋 수가 58회, 30일 기준으로는 224회에 달합니다. AI 에이전트를 활용한 워크플로우 최적화 작업이 얼마나 치열하게 진행되고 있는지를 수치로 확인할 수 있었습니다. 단순히 '열심히 했다'가 아니라, JSON 데이터로 정량화된 지표를 보면 다음 단계에서 어디에 더 집중해야 할지가 명확해집니다.

## 2. 생성형 AI의 함정: '글자'라는 거대한 벽을 넘어서

오늘 작업의 핵심은 박태원의 소설 「소설가 구보씨의 일일」을 분석하고 영상화하는 과정이었습니다. 특히 Flux 모델을 이용해 1934년 경성의 분위기를 구현하는 작업에서 예상치 못한 난관에 부딪혔습니다.

### 문제 상황: 과도한 '텍스트' 생성
1930년대 경성은 '간판의 시대'였습니다. AI에게 '1934년 경성'이라는 프롬프트를 주자, 모델은 충실하게(?) 거리의 모든 벽면과 액자, 현판을 정체불명의 글자들로 가득 채웠습니다. 결과적으로 **1차 생성분 88장 중 약 70장(80%)을 폐기**해야 하는 상황이 발생했습니다.

### 기술적 결정: 프롬프트 전략의 수정
무작정 다시 생성하는 것은 리소스 낭비입니다. 저는 프롬프트 전략을 다음과 같이 수정했습니다.

*   **지명 제거**: 구체적인 장소명(BASE)을 빼서 AI가 특정 간판을 그리려는 시도를 줄였습니다.
*   **부정 프롬프트 및 제약 조건 강화**: `plain bare walls, no frames, no calligraphy`와 같은 구체적인 제약 조건을 추가했습니다.
*   **구도 변경**: 정면 샷보다는 **클로즈업, 뒷모습, 빗길, 정물** 위주로 앵글을 틀었습니다.

그 결과, 2차 생성분 76장 중 55장을 사용할 수 있게 되었습니다. AI 모델의 특성을 파악하고, '그리지 말아야 할 것'을 정의하는 것이 '그려야 할 것'을 정의하는 것만큼 중요하다는 점을 다시 한번 깨달았습니다.

## 3. 엔지니어의 디테일: 쉘 스크립트의 작은 함정

작업 중 발견한 소소하지만 중요한 인사이트 하나를 공유합니다. 렌더링 완료를 확인하기 위해 `pgrep -f`를 사용하여 프로세스를 체크했는데, SSH를 통해 명령어를 실행하다 보니 **명령어를 실행 중인 SSH 셸 자체의 패턴이 잡혀** 프로세스가 영원히 끝나지 않는 루프에 빠지는 현상이 있었습니다.

```bash
# 위험한 접근: ssh ... 'pgrep -f 10_create_video'
# 해결책: 프로세스 이름이 아닌 로그 파일의 특정 문자열("영상 제작 완료")로 판정
```

결국 시스템의 상태를 확인할 때는 프로세스 리스트보다는 **애플리케이션이 남기는 명시적인 로그(Log)**를 신뢰하는 것이 가장 정확하다는 기본 원칙을 다시금 확인했습니다.

## 마치며

오늘의 작업은 데이터 업데이트라는 단순한 'chore'부터, AI 모델의 한계를 극복하는 'feat'까지 다양했습니다. 기술적 깊이는 결국 이런 작은 디테일과 시행착오를 어떻게 기록하고 개선하느냐에서 결정된다고 믿습니다.

씨피랩스에서도 이러한 데이터 중심의 사고와 AI 최적화 경험을 녹여내어, 더 효율적이고 견고한 시스템을 만들어 가겠습니다.
