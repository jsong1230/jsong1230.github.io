# [Dev Log] 자동화 드라이버 설계와 데이터 파이프라인의 정교함에 대하여

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 가장 희열을 느끼는 순간은 복잡한 수동 프로세스를 단순하고 견고한 자동화 스크립트로 치환했을 때입니다. 오늘은 제가 진행한 몇 가지 작업 중, 특히 운영 효율화를 위한 '빌드 드라이버' 작성과 개인 프로젝트의 데이터 관리 경험을 공유해보고자 합니다.

## 1. 반복되는 운영 작업을 '드라이버'로 추상화하기

오늘 가장 집중한 작업은 `heritageradio` 프로젝트의 주차별 빌드 및 검증 프로세스를 자동화하는 것이었습니다. 매주 반복되는 빌드 절차가 있지만, 날짜나 특정 조건에 따라 수동 개입이 필요한 경우가 많습니다. 이때 무작정 전체를 자동화하기보다, **'절차는 유지하되 변수만 교체하는 드라이버(Driver) 스크립트'** 방식을 채택했습니다.

이번에 작성한 `_oneoff_build_w24.sh`가 그 결과물입니다. 단순히 명령어를 나열한 것이 아니라, 다음과 같은 기술적 결정들을 포함했습니다.

### 기술적 결정과 인사이트
*   **순차 실행의 강제**: `workspace`가 날짜를 공유하기 때문에 병렬 실행 시 충돌이 발생합니다. 이를 방지하기 위해 `for` 루프를 통한 엄격한 순차 실행 구조를 설계했습니다.
*   **환경 격리를 통한 정합성 확보**: 호스트 머신(EC2)의 환경에 의존하지 않고, 모든 빌드와 검증을 Docker 컨테이너 내부에서 수행하도록 했습니다. 특히 `verify_cycle_content.py` 실행 시 GPU 호스트의 Whisper API와 연결되는 설정을 컨테이너 환경 변수로 주입하여, 환경 차이로 인한 `VERIFY_FAIL` 오탐을 원천 차단했습니다.
*   **효율적인 저장 공간 활용 (Hardlink)**: 일요일 데이터를 토요일 데이터의 하드링크(`cp -al`)로 처리함으로써, 저장 공간 낭비를 줄이면서도 파일 시스템 수준의 일관성을 유지했습니다.

```bash
# 흥미로운 부분: 하드링크를 이용한 일요일 데이터 생성
mkdir -p /app/hls/${sun_dd}; cp -al \$src \$dst
```

이처럼 "어디까지 자동화하고 어디서 수동 제어권을 가질 것인가"에 대한 고민이 운영 안정성을 결정짓는 핵심이라고 생각합니다.

## 2. 데이터 기반의 콘텐츠 큐레이션

개인 프로젝트인 `booksummary`에서는 테네시 윌리엄스의 「욕망이라는 이름의 전차」 업로드 작업을 진행했습니다. 단순한 업로드가 아니라, 사전 정의된 '수요/월'과 '경쟁률' 데이터를 바탕으로 우선순위를 정해 큐(Queue)를 관리하고 있습니다.

데이터 시트(`candidates.md`)에서 보듯, 단순한 감이 아니라 **[수요 $\div$ 경쟁]** 비율을 계산하여 효율이 가장 높은 콘텐츠부터 순차적으로 제작하는 파이프라인을 구축했습니다. 엔지니어링 관점에서 콘텐츠 제작 역시 하나의 '최적화 문제'로 접근하는 과정이 매우 즐겁습니다.

## 마치며

오늘의 작업들은 규모는 다르지만 본질적으로는 같습니다. **"반복되는 패턴을 찾아내고, 이를 시스템화하여 휴먼 에러를 줄이며, 데이터에 기반해 의사결정을 내리는 것"**입니다. 

Web3나 AI 같은 최첨단 기술을 다루는 것도 중요하지만, 결국 서비스의 완성도는 이런 기초적인 운영 자동화와 정교한 데이터 관리라는 '디테일'에서 결정된다고 믿습니다.

내일은 또 어떤 최적화 포인트가 기다리고 있을지 기대됩니다.
