# [Engineering Log] "명령줄만 봐서는 모른다" — 인프라 파괴 방지 가드의 진화

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 가장 아찔한 순간은 언제일까요? 아마도 '실수로' 운영 환경의 리소스를 삭제했을 때일 것입니다. 특히 AI 에이전트가 인프라 관리 도구로 활용되는 최근의 흐름 속에서는, 사람이 직접 치는 오타보다 **'에이전트가 생성한 스크립트의 실행'**이라는 새로운 형태의 위험 요소가 등장했습니다.

오늘은 제가 최근 겪은 인프라 사고를 바탕으로, 이를 원천적으로 차단하기 위해 구축한 **'Destructive-Command Guard'**의 고도화 과정을 공유하려 합니다.

### 1. 문제의 핵심: "숨어있는 파괴 명령"

기존의 가드 시스템은 사용자가 입력한 '명령줄(Command Line)'만을 검사했습니다. 예를 들어 `aws ec2 delete-volume`이라는 명령어가 들어오면 이를 감지해 차단하거나 승인을 요청하는 방식이었죠.

하지만 실제 사고는 다른 형태로 발생했습니다.
1. AI 에이전트가 `Write` 도구를 사용해 `cleanup.sh`라는 스크립트 파일을 생성합니다.
2. 이 파일 내부에는 리소스를 삭제하는 파괴적인 명령어가 들어있습니다.
3. 에이전트는 단순히 `bash cleanup.sh`라고 실행합니다.

가드 입장에서는 `bash cleanup.sh`라는 명령어 자체는 전혀 무해해 보입니다. 결과적으로 **명령줄만 검사하는 훅(Hook)은 스크립트 내부에 숨겨진 파괴 명령을 전혀 잡아내지 못했습니다.**

### 2. 기술적 결정: 스크립트 내부 재귀 스캔 (Deep Scan)

이 구멍을 막기 위해 저는 **PreToolUse(도구 실행 전 단계) 시점에 스크립트 파일의 내용을 직접 스캔**하는 로직을 추가했습니다.

**핵심 구현 로직:**
- **경로 추출:** 명령줄에서 `bash`, `sh`, `source` 등으로 호출되는 파일 경로를 추출합니다.
- **내용 검사:** 추출된 파일을 읽어 기존의 파괴적 명령어 패턴(`AWS_VERBS`, `rm -rf` 등)이 있는지 검사합니다.
- **재귀적 추적:** 스크립트가 또 다른 스크립트를 호출하는 경우를 대비해 **최대 3단계까지** 따라 들어가며 스캔합니다.

실제 구현된 코드의 일부입니다:
```bash
scan_script() {
  local f="$1" depth="${2:-0}" body nested n
  [ "$depth" -gt 3 ] && return 0                      # 순환·과도한 재귀 방지
  [ -f "$f" ] && [ -r "$f" ] || return 0
  body=$(head -c 262144 -- "$f" 2>/dev/null) || return 0
  
  # 파괴적 패턴 검사
  if printf '%s' "$body" | grep -E 'aws ' | grep -qE "$AWS_VERBS" \
    || printf '%s' "$body" | grep -qE 'aws-safe-delete[[:space:]]+(volume|instance)' \
    || printf '%s' "$body" | grep -qE '(^|[;&|][[:space:]]*)rm[[:space:]]+-[a-zA-Z]*r'; then
    SCRIPT_HIT="$f"
    return 1
  fi
  # 중첩 스크립트 추적
  nested=$(printf '%s' "$body" | grep -oE '[^[:space:];&|<>"'"'"']+\.sh' | sort -u)
  for n in $nested; do
    scan_script "$n" $((depth + 1)) || return 1
  done
  return 0
}
```

### 3. 시행착오와 인사이트: "자기 발등 찍기"

개발 과정에서 흥미로운 문제가 하나 발생했습니다. 가드를 테스트하기 위한 `test-cpdax-guard.sh` 파일 자체가 파괴적 명령어들을 '테스트 데이터'로 담고 있다 보니, **가드가 테스트 스크립트 실행 자체를 차단**해버리는 상황이 발생한 것입니다.

이를 해결하기 위해 저는 `GUARD_SCAN_EXEMPT`라는 명시적 예외 선언 방식을 도입했습니다. 스크립트 상단 10줄 이내에 이 선언이 있으면 스캔을 건너뛰도록 설계했습니다.

여기서 중요한 점은 **'은닉 불가'**입니다. 이 선언은 코드 리뷰 시 diff에 명확히 드러나야 하며, 실제 운영 스크립트에는 절대 넣지 않는다는 엄격한 규칙을 세웠습니다. 편의성과 보안 사이의 트레이드오프를 '명시적 선언과 리뷰'라는 프로세스로 해결한 셈입니다.

### 마치며

이번 작업을 통해 다시 한번 느낀 점은, 시스템의 보안은 '가장 약한 고리'에서 결정된다는 것입니다. 명령줄이라는 겉모습만 보는 것이 아니라, 실제 실행될 '본질(내용)'을 들여다보는 관점이 필요했습니다.

비록 `eval`이나 `base64` 난독화 같은 한계점은 여전히 남아있지만, 실제 발생했던 사고 패턴을 100% 차단했다는 점에서 큰 의미가 있었습니다. 앞으로도 씨피랩스에서 더 안전하고 견고한 인프라 자동화 환경을 만들어가겠습니다.
