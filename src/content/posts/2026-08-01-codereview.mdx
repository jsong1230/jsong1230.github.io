시니어 소프트웨어 엔지니어로서 오늘의 커밋과 코드 변경 사항을 리뷰하겠습니다.

이번 작업은 단순한 데이터 업데이트부터, 실제 장애(7/31 bp3 outage)의 원인을 분석하고 이를 기술적으로 해결하기 위한 자동화 도구 작성까지 폭넓은 범위의 개선이 포함되어 있습니다. 특히 **"장애 발생 $\rightarrow$ 원인 분석 $\rightarrow$ 재발 방지책 설계 $\rightarrow$ 자동화 도구 구현"**으로 이어지는 엔지니어링 프로세스가 매우 훌륭합니다.

---

## ✅ 잘한 점

1. **철저한 장애 분석 기반의 해결책 설계**
   - 단순히 "트리거가 안 된다"에서 끝내지 않고, `net.tcp.service` (Simple check)가 왜 BP 노드에서 작동하지 않았는지(`127.0.0.1` 바인딩 문제)를 정확히 짚어냈습니다.
   - 특히 **실패 양상의 분리**(`systemd` 상태를 통한 프로세스 사망 탐지 vs `chain_head_block`을 통한 로직 정지 탐지)를 통해 탐지 정밀도를 높인 설계가 매우 탁월합니다.

2. **엣지 케이스(EN2 노드) 고려 및 정교한 적용 범위 설정**
   - 템플릿 레벨에서 일괄 비활성화를 하지 않고, `0.0.0.0` 바인딩으로 인해 기존 체크가 유효한 `EN2` 노드를 보호하기 위해 **호스트 레벨 비활성화**라는 정교한 전략을 선택했습니다. 이는 시스템 전체의 가시성을 유지하려는 시니어 수준의 세심한 결정입니다.

3. **보안 및 운영 안정성을 고려한 도구 설계**
   - `ZBX_TOKEN` 환경변수나 `stdin`을 통해 자격증명을 처리함으로써 `ps` 명령어로 노출될 수 있는 `argv` 보안 취약점을 사전에 차단했습니다.
   - `dry-run`을 기본값으로 설정하고 `--apply`, `--revert` 옵션을 제공하여, 인프라 변경 작업 시 발생할 수 있는 휴먼 에러를 최소화하고 롤백 경로를 확보했습니다.

4. **상세한 기록(Documentation)**
   - `logs/2026-08-01.md`에 403/503 에러의 원인(vhost 설정 문제)부터 API 엔드포인트 규명 과정까지 상세히 기록하여, 추후 동일한 네트워크 트러블슈팅 시 훌륭한 레퍼런스가 되도록 작성했습니다.

## 🔧 개선할 점

1. **스크립트 내 하드코딩된 설정 값의 외부화**
   - `BP_HOSTS`, `URL`, `TEMPLATE` 등이 스크립트 상단에 하드코딩되어 있습니다. 현재는 단일 목적의 도구라 무방하지만, 향후 다른 환경(Mainnet 등)으로 확장될 가능성이 있다면 별도의 `config.json`이나 환경변수로 분리하는 것이 유지보수에 유리합니다.

2. **에러 핸들링의 구체화**
   - `call()` 함수 내에서 `urllib.request`를 사용하고 있는데, 네트워크 타임아웃이나 Zabbix API의 비즈니스 로직 에러(예: 권한 부족, 존재하지 않는 hostid) 발생 시 사용자에게 더 구체적인 가이드를 제공하는 예외 처리 로직이 보강되면 좋겠습니다.

3. **데이터 업데이트 커밋의 원자성**
   - `chore: Update dashboard data` 커밋에서 여러 레포지토리의 통계가 한꺼번에 변경되었습니다. 자동 생성되는 파일이라 어쩔 수 없는 부분일 수 있으나, 변경량이 많을 경우 어떤 레포지토리의 데이터가 핵심적으로 변했는지 파악하기 어렵습니다. (물론 JSON 파일 특성상 불가피한 면이 있습니다.)

## 💡 오늘의 기술 포인트

**"다층적 모니터링 전략 (Multi-layered Monitoring Strategy)"**
오늘 작업의 핵심은 **'프로세스가 떠 있는가(Liveness)'**와 **'프로세스가 실제로 일을 하고 있는가(Readiness/Health)'**를 분리하여 측정했다는 점입니다. 
- `systemd.unit.info`: 프로세스의 생존 여부 확인 (Liveness Probe)
- `metadium[chain_head_block]`: 데이터의 흐름 확인 (Health Check)

이 패턴은 분산 시스템이나 블록체인 노드처럼 프로세스는 살아있지만 내부 락(Lock)이나 네트워크 이슈로 인해 '좀비 상태'가 될 수 있는 서비스에서 반드시 적용해야 하는 필수적인 모니터링 패턴입니다.
