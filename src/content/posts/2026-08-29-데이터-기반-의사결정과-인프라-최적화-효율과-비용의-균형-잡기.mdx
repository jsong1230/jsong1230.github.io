# [Engineering Log] 데이터 기반의 의사결정과 인프라 최적화: 효율과 비용의 균형 잡기

안녕하세요, 씨피랩스의 CTO 송주한입니다.

개발자의 일상은 단순히 코드를 짜는 것에 그치지 않습니다. 때로는 수천 개의 데이터를 분석해 비즈니스 기준을 세우고, 때로는 클라우드 비용의 소수점 단위까지 추적하며 최적의 효율을 찾아내는 과정의 연속이죠. 오늘은 제가 진행한 세 가지 서로 다른 성격의 작업—**콘텐츠 가이드라인 수립, 인프라 비용 최적화, 그리고 데이터 기반의 후보군 발굴**—을 통해 느낀 인사이트를 공유해 보려 합니다.

---

### 1. "완벽함보다 중요한 것은 비용 대비 효용이다" (Heritage Radio)

최근 진행 중인 프로젝트에서 오디오 슬롯 초과 문제가 발생했습니다. 일부 콘텐츠의 길이가 기준을 넘어 뒷부분(날씨 및 클로징)이 잘리는 현상이 발견된 것이죠. 엔지니어로서의 본능은 "모든 오류를 수정하고 재빌드하는 것"이었지만, 실무적인 관점에서 다시 생각했습니다.

이미 검증과 프리즈(Freeze)가 완료된 10일치 분량을 단 22편의 수정을 위해 다시 흔드는 것은 리스크와 비용이 너무 컸습니다. 결국 **'소급 정리 대신 향후 기준 전달'**이라는 결정을 내렸습니다.

여기서 흥미로운 점은 단순히 "그냥 둔다"가 아니라, **데이터에 기반한 정교한 가이드라인**을 제시했다는 것입니다.

> **Era별 권장 상한(공백 제외):**
> 1955(2,400자) / 1965(2,550자) / 1985(2,650자) / 1975(2,750자) / 1995(2,900자)
> $\text(기준) = \text(실측 낭독속도) \times 570\text(초)$

시대별 낭독 속도가 다르다는 점을 실측 데이터로 증명하고, 이를 수치화하여 전달함으로써 향후 발생할 문제를 원천 차단했습니다. 기술적 해결책이 항상 '코드 수정'일 필요는 없습니다. 때로는 정확한 '기준의 정의'가 더 효율적인 해결책이 됩니다.

### 2. 인프라 관리: 보이지 않는 비용의 누수를 막는 법 (Ops)

클라우드 비용 최적화는 끝이 없는 싸움입니다. 오늘은 만료된 스냅샷을 삭제하고, 대규모 데이터를 Archive 티어로 전환하는 작업을 진행했습니다.

특히 이번에 구현한 `gmet-fleet-status.sh` 도구가 기억에 남습니다. 전 계층의 노드 상태를 한눈에 점검하기 위해 만들었는데, 개발 과정에서 작은 함정을 발견했습니다.

```bash
# 함정 기록: 플릿 gmet은 PATH에 없음(/opt/meta/bin/gmet) 
# `command -v` 의존 시 전 노드 거짓 IPC_UNAVAILABLE 발생
```

환경 변수(`PATH`)에 의존하지 않고 절대 경로를 통해 바이너리를 호출해야 한다는 기본적이지만 중요한 레슨을 다시금 깨달았습니다. 결과적으로 불필요한 스냅샷 삭제와 티어 전환을 통해 월 비용을 절감하며, 인프라의 건강 상태(Health Check)를 자동화할 수 있었습니다.

### 3. 데이터의 '흔들림'을 해석하는 관점 (Book Summary)

마지막으로 도서 요약 서비스의 후보군을 발굴하는 작업입니다. 유튜브 검색 데이터를 통해 '경쟁 중간값'을 측정하는데, 여기서 데이터의 **'불안정성'**을 어떻게 처리할 것인가가 핵심이었습니다.

특정 도서는 재측정 시 값이 크게 튀는 현상이 있었습니다. 저는 이를 '데이터 오류'로 치부하는 대신, **'측정 안정성'이라는 새로운 필터**로 활용했습니다.

- **안정적인 데이터:** 2~3회 측정 시 오차 0.3% 이내 $\rightarrow$ 신뢰하고 착수
- **불안정한 데이터:** 측정 시마다 값의 변동이 심함 $\rightarrow$ 리스크가 큰 후보군으로 분류하여 제외

데이터가 흔들린다는 사실 자체가 하나의 정보가 된 셈입니다.

### 마치며: 엔지니어의 시선

오늘의 작업들을 관통하는 키워드는 **'최적화'**입니다. 
- **시간의 최적화:** 불필요한 재작업을 피하고 기준을 세우는 것.
- **비용의 최적화:** 사용하지 않는 자원을 찾아내고 티어를 조정하는 것.
- **전략의 최적화:** 데이터의 변동성을 분석해 성공 확률이 높은 후보를 고르는 것.

20년 넘게 엔지니어로 일하며 배운 점이 있다면, 최고의 기술은 가장 복잡한 코드를 짜는 것이 아니라, **현재 상황에서 가장 적은 비용으로 최대의 효과를 내는 지점을 찾아내는 능력**이라는 것입니다.

내일은 또 어떤 최적화 포인트가 기다리고 있을지 기대됩니다.
