# [Dev Log] 데이터의 흐름으로 기록하는 성장: 대시보드 자동화의 가치

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한(Jeffrey)입니다.

엔지니어로 20년 넘게 커리어를 쌓아오며 제가 가장 중요하게 생각하는 것 중 하나는 '가시화(Visualization)'입니다. 복잡한 시스템의 아키텍처를 다이어그램으로 그리는 것만큼이나, 개인의 성장 궤적과 작업 패턴을 데이터로 확인하는 것은 매우 강력한 동기부여가 됩니다.

오늘은 제 개인 대시보드(`jsong1230.github.io`)의 데이터를 업데이트하며, 제가 왜 이런 자동화된 기록 시스템을 유지하는지에 대해 이야기해보려 합니다.

### 단순한 업데이트, 그 이상의 의미

오늘의 작업은 겉보기에 단순한 `chore: Update dashboard data`였습니다. `dashboard.json` 파일의 내용을 최신화하는 작업이었죠. 하지만 이 JSON 데이터가 담고 있는 내용은 결코 단순하지 않습니다.

```json
{
  "name": "claude-agent",
  "last_date": "2026-11-05",
  "last_msg": "log: 11/04 briefick entries re-registered, CTO not under T-Flow",
  "activity": [8, 2, 15, 27, 5, 17, 0],
  "commits_7d": 100,
  "commits_30d": 476
}
```

위의 diff 내용을 보면 `claude-agent`라는 리포지토리의 활동량이 눈에 띕니다. 최근 7일간 100개의 커밋, 30일간 476개의 커밋이 기록되었습니다. 특히 `activity` 배열에 나타난 일별 커밋 수의 변동폭을 보면, 특정 시점에 집중적으로 몰입하여 문제를 해결했던 흔적이 고스란히 드러납니다.

### 기술적 결정: 왜 정적 데이터 기반의 대시보드인가?

많은 분이 API를 통해 실시간으로 GitHub 데이터를 가져오는 방식을 선택합니다. 하지만 저는 의도적으로 `dashboard.json`이라는 정적 파일을 생성하고 업데이트하는 방식을 택했습니다. 여기에는 몇 가지 엔지니어링적 판단이 있었습니다.

1. **성능과 비용**: 매번 페이지를 로드할 때마다 외부 API를 호출하는 것은 불필요한 레이턴시를 발생시킵니다. 빌드 타임에 데이터를 생성해두면 사용자(혹은 나 자신)는 즉각적인 응답 속도를 경험할 수 있습니다.
2. **스냅샷의 가치**: API는 '현재'의 상태를 보여주지만, Git으로 관리되는 JSON 파일은 '시간의 흐름'을 기록합니다. 특정 시점에 내가 어떤 프로젝트에 얼마나 몰입했는지를 Git history를 통해 역추적할 수 있다는 점이 가장 큰 매력입니다.
3. **단순함의 미학**: 복잡한 백엔드 서버 없이 GitHub Actions와 정적 페이지(GitHub Pages)만으로 전체 파이프라인을 구축함으로써, 유지보수 비용을 제로에 가깝게 낮췄습니다.

### 인사이트: 기록은 기억을 이긴다

이번 업데이트를 통해 다시 한번 느낀 점은, **"측정할 수 없으면 개선할 수 없다"**는 격언입니다. 

단순히 "요즘 AI 에이전트 개발에 시간을 많이 쓰고 있다"라고 느끼는 것과, `commits_30d: 476`이라는 숫자를 확인하는 것은 완전히 다른 경험입니다. 데이터는 저의 몰입도를 객관적으로 증명해주며, 동시에 어떤 프로젝트가 정체되어 있는지(예: `heritageradio`의 낮은 활동성)를 알려주는 신호등 역할을 합니다.

씨피랩스에서 수많은 Web3, AI 프로젝트를 리딩하며 제가 팀원들에게 항상 강조하는 것도 바로 이러한 '데이터 기반의 사고'입니다. 기술적인 결정이 직관에만 의존하지 않고, 실제 지표와 기록에 근거할 때 비로소 팀은 정교하게 성장할 수 있기 때문입니다.

오늘의 작은 커밋 하나가 모여 저의 기술적 자산이 되고, 그것이 다시 새로운 인사이트로 이어지는 선순환. 이것이 제가 매일 기록을 멈추지 않는 이유입니다.
