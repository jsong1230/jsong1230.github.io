# [DevLog] 온체인 밸리데이터 운영의 쓴맛과 단맛: 슬래싱 복구와 자동화 도구 제작

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey)입니다.

최근 밸리데이터 노드를 운영하며 뼈아픈 장애 상황을 겪었습니다. OOM(Out Of Memory)으로 인한 노드 정지와 그로 인해 이어진 자동 슬래싱(Slashing) 및 킥아웃(Kick-out) 상황이었죠. 오늘은 이 장애를 분석하고, 다시 정상 궤도로 복구하기 위해 진행한 기술적 작업들을 정리해 보려 합니다.

### 1. 문제의 핵심: "왜 선출되지 않았는가?"

장애 복구 후 노드를 재기동했지만, Active 상태임에도 불구하고 블록 생산자(Validator)로 선출되지 않는 문제가 발생했습니다. 원인을 분석해 보니, 슬래싱으로 인해 `bond` 금액이 런타임 요구 조건인 400,000 BFC 미만으로 떨어졌기 때문이었습니다.

온체인 데이터 확인 결과, 정확히 4,000 BFC가 슬래싱되었고 이 작은 차이가 '선출 제외'라는 결과로 이어졌습니다. 결국 부족분을 채우기 위해 `candidateBondMore` 트랜잭션을 실행해야 하는 상황이었습니다.

### 2. 기술적 결정: 안전을 최우선으로 한 서명 도구 제작

단순한 트랜잭션 하나지만, 밸리데이터의 Stash 계정은 매우 민감한 자산입니다. GUI 기반의 지갑이나 검증되지 않은 스크립트를 쓰기보다, 제가 직접 제어할 수 있는 최소한의 서명 도구를 작성하기로 했습니다.

이번에 작성한 `bond-more.mjs` 스크립트에서 가장 신경 쓴 부분은 **'안전 장치'**입니다.

```javascript
// 1. 주소 검증: 엉뚱한 계정으로 전송하는 사고 방지
if (!addr.startsWith(EXPECT_PREFIX) || !addr.endsWith(EXPECT_SUFFIX)) {
  console.error('⛔ stash 주소 불일치 — 중단'); process.exit(3);
}

// 2. Dry-run 기본 설정: 실행 전 상태 확인 필수
if (!EXECUTE) { 
  console.log('dry-run 종료 (--execute 로 제출)'); 
  await api.disconnect(); 
  process.exit(0); 
}
```

**주요 설계 포인트:**
- **Dry-run by Default:** `--execute` 플래그를 명시적으로 넣지 않으면 절대 트랜잭션을 제출하지 않습니다. 주소 확인, 잔고 조회, 수수료 추정까지만 수행합니다.
- **Strict Address Check:** `EXPECT_PREFIX`와 `EXPECT_SUFFIX`를 통해 서명하는 계정이 정확히 우리가 의도한 Stash 계정인지 한 번 더 검증합니다.
- **Memory Safety:** 키 파일에서 읽어온 헥사 값은 사용 직후 `null` 처리하여 메모리 덤프 등을 통한 유출 가능성을 최소화했습니다.

### 3. 인사이트: 인프라 모니터링의 공백을 깨닫다

이번 장애 리포트를 작성하며 킥아웃 시각을 추가하는 작업을 했습니다. 9월 30일 19:29에 노드가 정지되었지만, 정작 워치독 알림이 온 것은 22:07이었습니다. 

Docker 컨테이너가 `running` 상태임에도 내부 프로세스가 죽어있는 '좀비 상태'를 감지하지 못한 것이 치명적이었습니다. 단순히 프로세스의 생존 여부를 확인하는 것을 넘어, RPC 응답성이나 블록 높이 업데이트 여부를 체크하는 **Liveness Probe**의 중요성을 다시 한번 절감했습니다.

### 마치며

인프라 운영에서 가장 위험한 것은 '당연히 작동하겠지'라는 믿음입니다. 이번 경험을 통해 모니터링 체계를 보완하고, 긴급 상황에서 실수 없이 대응할 수 있는 전용 툴링의 필요성을 느꼈습니다. 

씨피랩스는 앞으로도 이러한 실무 경험을 바탕으로 더 견고한 Web3 인프라를 구축해 나가겠습니다.
