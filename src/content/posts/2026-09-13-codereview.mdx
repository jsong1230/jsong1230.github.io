안녕하세요, 시니어 소프트웨어 엔지니어이자 코드 리뷰어입니다.

오늘 제출하신 커밋들은 단순한 코드 변경을 넘어, **데이터의 정합성을 검증하는 프로세스와 도메인 지식을 시스템화하는 과정**이 돋보이는 작업들입니다. 특히 `heritageradio`와 `booksummary` 두 프로젝트에서 보여준 '검증 기반의 의사결정' 방식이 매우 인상적입니다.

상세 리뷰를 작성해 드립니다.

---

## ✅ 잘한 점

### 1. 철저한 팩트 체크와 데이터 검증 (heritageradio)
단순히 기존 자료를 옮기는 것이 아니라, **음력/양력 환산 오류(성철 스님)**, **출처가 불분명한 통설(피사의 사탑)**, **사후에 덧붙여진 명언** 등을 직접 검증하여 필터링한 점이 훌륭합니다. 이는 콘텐츠의 신뢰도를 결정짓는 핵심적인 엔지니어링적 접근(Data Validation)과 같습니다.

### 2. 정성적 분석과 정량적 지표의 조화 (booksummary)
`screen_candidates.py`를 도입하면서 단순히 '비율(Ratio)'이라는 정량적 지표에 의존하지 않고, **"제안어 13개가 꽉 찬 것 자체가 수요 신호"**라는 정성적 패턴을 발견하여 이를 가이드라인에 반영한 점이 매우 날카롭습니다. 데이터가 주는 함정(False Positive)을 실제 사례(원미동 사람들)를 통해 빠르게 잡아내고 수정하는 피드백 루프가 매우 빠릅니다.

### 3. 엣지 케이스(Edge Case) 정의 및 분류
`booksummary`에서 게이트 초과 유형을 **'진동형'**과 **'안정 초과형'**으로 정의한 점이 탁월합니다. 이는 불확실성(Variance)이 높은 데이터와 확정적인 데이터를 구분하여, 불필요한 재측정 비용을 줄이는 효율적인 분류 체계입니다.

### 4. 투명한 기록과 히스토리 관리
`candidates.md`에 탈락 사유(예: 오발탄 $\rightarrow$ 소곱창전골 식당)를 구체적으로 기록하여, 나중에 다른 작업자가 보더라도 왜 이 데이터가 제외되었는지 즉시 알 수 있게 한 '문서화 습관'이 시니어 수준의 디테일입니다.

## 🔧 개선할 점

### 1. 스크립트 내 하드코딩된 비즈니스 로직 (screen_candidates.py)
현재 `screen_candidates.py`의 독스트링과 주석에 매우 중요한 판정 기준(비율 0.4의 함정, 제안어 읽는 법 등)이 적혀 있습니다. 
- **개선 제안:** 이 기준들을 단순 주석이 아니라, 스크립트 실행 시 `--verbose` 모드에서 **"주의: 비율이 낮더라도 제안어에 '내신/수특' 키워드가 있으면 검토하십시오"**와 같은 경고 메시지로 출력하게 하여, 분석가가 실수로 정량 지표만 보고 판단하는 것을 방지하는 안전장치를 마련하면 좋겠습니다.

### 2. 대규모 JSON 파일의 수동 업데이트 (dashboard.json)
`dashboard.json`의 변경 사항을 보면 `activity` 배열과 `commits_7d` 등의 수치를 수동으로 업데이트하고 계신 것으로 보입니다.
- **개선 제안:** 현재 `gram-jsong` 머신에서 여러 레포지토리를 관리하고 계시므로, Git API나 로컬 `git log`를 분석해 `dashboard.json`을 자동으로 생성하는 간단한 쉘 스크립트나 파이썬 스크립트를 작성하시길 권장합니다. 휴먼 에러를 줄이고 작업 시간을 단축할 수 있습니다.

### 3. 커밋 메시지의 일관성
`[admin] docs: ...`와 같은 형식과 `chore: ...`, `feat: ...` 형식이 혼용되고 있습니다. 
- **개선 제안:** 프로젝트별로 컨벤션을 다르게 가져가는 것이 아니라면, 전체적으로 `type(scope): message` 형태(Conventional Commits)로 통일하여 나중에 자동 릴리즈 노트 생성 등이 가능하도록 구조화하시길 추천합니다.

## 💡 오늘의 기술 포인트

### 🛠️ "Human-in-the-loop" 필터링 패턴
오늘 작업의 핵심은 **[자동 스크리닝 $\rightarrow$ 인간의 패턴 인식 $\rightarrow$ 필터링 기준 수정 $\rightarrow$ 최종 확정]**으로 이어지는 파이프라인입니다. 

특히 `screen_candidates.py`를 통해 1차적으로 쿼터(Quota) 소모를 방지하고, 고비용의 정밀 측정(`measure_search_supply.py`) 전 단계에 '가벼운 필터'를 배치한 설계는 리소스 최적화 관점에서 매우 효율적인 선택입니다. 이는 대규모 데이터 전처리 과정에서 흔히 쓰이는 **'Cascading Filter'** 패턴의 실전 적용 사례라고 볼 수 있습니다.
