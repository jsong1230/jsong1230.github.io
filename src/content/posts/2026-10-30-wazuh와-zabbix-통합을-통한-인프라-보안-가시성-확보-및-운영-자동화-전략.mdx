# [Dev Log] 인프라 가시성의 완성: Wazuh-to-Zabbix 통합과 운영 자동화의 디테일

안녕하세요, 씨피랩스 CTO 송주한(Jeffrey)입니다.

엔지니어로서 가장 희열을 느끼는 순간은 복잡하게 얽혀 있던 데이터 흐름이 하나의 대시보드 위에서 명확한 지표로 시각화될 때입니다. 오늘은 보안 솔루션인 Wazuh와 모니터링 툴인 Zabbix를 연동하여 인프라의 보안 상태를 실시간으로 추적하는 'Wazuh-to-Zabbix' 통합 작업의 3단계 고도화 과정을 진행했습니다.

단순한 연결을 넘어, 실제 운영 환경에서 발생할 수 있는 '노이즈'를 어떻게 줄이고 '정확한 신호'만 남길 것인가에 대한 고민이 깊었던 하루였습니다.

### 1. 오늘의 핵심 과제: 보안 지표의 정밀한 시각화
오늘의 주된 목표는 Wazuh의 매니저 및 에이전트 상태 지표를 Zabbix로 가져와, 장애 발생 시 즉각적인 대응이 가능하도록 트리거를 설정하는 것이었습니다.

특히 **Stage 3**에서는 다음과 같은 세부 지표들을 정의했습니다:
- **에이전트 상태**: Active, Disconnected, Never Connected 수치 추적
- **취약점 및 보안**: `vuln_ok` 상태 및 리부팅 필요 여부 확인
- **커널 레벨 모니터링**: Critical/High 레벨의 커널 이슈 추적

### 2. 기술적 결정과 시행착오: "단일 이벤트 vs 다중 이벤트"
작업 과정에서 흥미로운 기술적 포인트가 하나 있었습니다. 바로 Zabbix 트리거의 **이벤트 생성 모드(Event generation mode)** 설정입니다.

초기에 트리거 원형을 `type=1(다중 이벤트)`로 설정했는데, 이로 인해 `nodata` 타이머가 평가될 때마다 새로운 PROBLEM 이벤트가 계속 생성되는 현상이 발생했습니다. 운영자 입장에서는 동일한 장애에 대해 수십 개의 알림을 받는 '알림 지옥'에 빠질 수 있는 상황이었죠.

```diff
- ★내 실수: 트리거 원형을 type=1(다중 이벤트)로 만듦 → nodata 타이머 평가(30s)마다 새 PROBLEM 이벤트(4건 관찰)
+ → 원형 27991~27993 type=0 으로 수정.
```

이를 `type=0(단일 이벤트)`로 빠르게 수정하여, 하나의 문제가 해결될 때까지 단 하나의 알림만 유지되도록 최적화했습니다. 인프라 엔지니어링에서 '정확한 알림'은 '많은 알림'보다 훨씬 가치 있다는 점을 다시 한번 상기한 지점이었습니다.

### 3. 운영 효율을 위한 자동화 툴링
코드 변경 사항 중에는 `zbx-cplabs-board.py` 스크립트 수정 건이 있습니다. 기존에는 `agent.ping` 기반으로 에이전트 생존 여부를 판단했는데, 이를 실제 **Active Agent Availability** 기반으로 변경했습니다.

또한, `gh-user-token` 헬퍼를 도입하여 키링(keyring) 라이브러리로 인해 프로세스가 멈추는(hanging) 현상을 방지하고, `hosts.yml`에서 직접 토큰을 읽어오도록 구조를 개선했습니다. 작은 변경 같지만, 자동화 파이프라인의 안정성을 높이는 데 결정적인 역할을 합니다.

### 4. 마치며: 데이터로 증명하는 엔지니어링
오늘 업데이트한 `dashboard.json`을 보면 `claude-agent` 리포지토리의 활동량이 급증한 것을 볼 수 있습니다. AI 에이전트를 활용한 Ops 작업이 단순한 실험을 넘어 실제 인프라 관리의 핵심 워크플로우로 자리 잡고 있음을 체감합니다.

**오늘의 인사이트:**
- **Less is More**: 모니터링의 핵심은 모든 것을 보는 것이 아니라, 봐야 할 것만 정확히 보는 것이다.
- **Edge Case의 중요성**: 키링 멈춤 현상 같은 작은 디테일이 전체 자동화 시스템의 신뢰도를 결정한다.

내일은 오늘 설정한 3단계 지표들이 실제 환경에서 어떻게 발화하고 억제되는지, 그 정밀도를 검증하는 작업에 집중할 예정입니다.
