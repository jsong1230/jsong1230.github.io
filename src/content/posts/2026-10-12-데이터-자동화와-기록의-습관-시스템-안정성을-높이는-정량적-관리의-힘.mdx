# [Dev Log] 데이터 자동화와 인프라 가시성: 작은 기록이 만드는 시스템의 안정성

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 20년 넘게 커리어를 쌓아오며 제가 가장 경계하는 것 중 하나는 '막연한 상태의 시스템'입니다. "아마 잘 돌아가고 있을 거야"라는 추측은 장애 상황에서 가장 위험한 적이 됩니다. 그래서 저는 개인적인 대시보드 관리부터 사내 인프라 모니터링까지, 모든 상태를 '데이터화'하고 '기록'하는 습관을 유지하고 있습니다.

오늘은 제가 진행한 두 가지 작업—개인 개발 활동의 데이터 업데이트와 사내 메인넷 플릿(Fleet) 상태 점검—을 통해 느낀 인사이트를 공유하고자 합니다.

### 1. 정량적 기록의 힘: 대시보드 데이터 업데이트

먼저 개인 깃허브 페이지(`jsong1230.github.io`)의 대시보드 데이터를 업데이트했습니다. 단순히 숫자를 바꾸는 작업처럼 보이지만, 이는 제가 어떤 기술적 관심사에 시간을 쏟고 있는지 객관적으로 파악하는 과정입니다.

이번 `dashboard.json` 변경 사항을 보면 흥미로운 점이 있습니다.
```json
- "last_msg": "런북: 정상 상태 메모리 기준선(10/10 실측)",
+ "last_msg": "잔존 정지 컨테이너 2개 정리, telegram-bot 정지 유지",
```
단순히 기능을 구현하는 것보다, **'정상 상태의 기준선(Baseline)'을 설정하고 불필요한 리소스를 정리하는 '운영적 최적화'**에 집중했음을 알 수 있습니다. 특히 `claude-agent` 리포지토리의 높은 커밋 활동량은 최근 AI 에이전트의 실무 적용 가능성을 깊게 탐구하고 있음을 보여줍니다.

### 2. 인프라 가시성 확보: gmet 플릿 서베이(Fleet Survey)

이어서 씨피랩스에서 관리하는 `gmet` 노드들의 상태를 전수 조사했습니다. 25개 유닛의 버전, 블록 높이, 피어(Peer) 수, 그리고 사용 중인 DB 엔진(RocksDB vs LevelDB)까지 상세히 기록했습니다.

특히 이번 로그에서 주목할 부분은 **'실패의 기록'**입니다.
```text
+n183|사내 follower(testnet)|...|Fatal: Unable to attach to remote geth: dial unix /home/jsong/.ethereum/gmet.ipc: connect: no such file or directory|LevelDB
+gpusrv150|게이트1 clean sync / localnet|-|접속실패 또는 gmet 프로세스 없음
```
모든 노드가 정상인 상태보다, `n183` 노드의 IPC 연결 실패나 `gpusrv150`의 프로세스 부재 같은 **'비정상 상태'가 명확히 기록된 데이터가 훨씬 가치 있습니다.** 그래야만 다음 작업의 우선순위가 결정되기 때문입니다.

### 기술적 결정과 인사이트

오늘의 작업들을 관통하는 핵심은 **"가시성(Visibility)"**입니다.

1. **데이터 기반의 회고**: `dashboard.json`처럼 내 활동을 정량화하면, 내가 어디에 과몰입하고 있고 어디를 놓치고 있는지 알 수 있습니다.
2. **상태의 명문화**: 인프라 점검 결과를 단순히 "이상 없음"으로 치부하지 않고, 각 노드의 상세 스펙과 에러 메시지를 텍스트 파일로 남기는 것은 추후 장애 발생 시 결정적인 '타임라인'이 됩니다.

Web3와 블록체인 인프라는 24시간 멈추지 않고 돌아가야 합니다. 그렇기에 엔지니어에게 필요한 것은 화려한 코드 한 줄보다, **시스템의 현재 상태를 정확하게 읽어낼 수 있는 정교한 기록 체계**라는 것을 다시 한번 느낍니다.

내일은 오늘 발견한 `n183` 노드의 연결 이슈를 해결하며, 다시 한번 '정상 상태'의 기준선을 맞춰보겠습니다.
