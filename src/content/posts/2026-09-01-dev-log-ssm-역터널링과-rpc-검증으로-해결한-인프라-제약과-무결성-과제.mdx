# [Dev Log] 인프라의 틈새를 메우는 기술: SSM 역터널링과 RPC 정밀 검증

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey)입니다.

엔지니어로 오래 일하다 보면, 화려한 신기술 도입보다 더 짜릿한 순간이 있습니다. 바로 **"제한된 환경 속에서 가장 효율적이고 안전한 우회로를 찾아내 문제를 해결했을 때"**입니다. 어제와 오늘, 저는 정확히 그 지점에 있는 두 가지 과제를 해결했습니다.

하나는 LLM 데모를 위한 네트워크 터널링 구축이었고, 다른 하나는 메인넷 업데이트 전 RPC 인터페이스의 무결성을 검증하는 작업이었습니다.

---

### 1. GPU 서버를 VPC 내부로: SSH-over-SSM 역터널링

최근 `daepa` 데모를 위해 사내 GPU 서버(H100 NVL x2)에 서빙 중인 `gemma-4-31b-it` 모델을 AWS VPC 내부의 앱에서 호출해야 하는 상황이었습니다.

**문제는 보안과 비용이었습니다.** 
VPC 내부에 NAT Gateway나 Endpoint를 구축하면 매달 수십 달러의 고정 비용이 발생하고, 외부에서 내부로 들어오는 인바운드 포트를 여는 것은 보안 정책상 금기입니다.

**기술적 결정: "역방향 SSH 터널링 + SSM"**
저는 `cplabs.io`에서 이미 검증된 패턴을 응용했습니다. 사내 GPU 서버가 AWS SSM(Systems Manager)을 통해 VPC 내의 아주 작은 `t4g.micro` 인스턴스로 먼저 접속하여 역터널을 뚫는 방식입니다.

- **구조:** `[GPU 서버] → (SSH-over-SSM) → [t4g.micro (10.0.0.4:18002)] ← [데모 앱]`
- **핵심 인사이트:** 
  - **비용 최적화:** NAT Gateway($40+) 대신 Public IP($3.65)와 소형 인스턴스를 활용해 월 비용을 $12 수준으로 낮췄습니다.
  - **보안 강화:** SSH 22번 포트를 완전히 닫고, 오직 SSM Session Manager를 통해서만 관리 접근이 가능하게 설정했습니다. 또한 터널링 전용 키에 `restrict` 옵션을 부여해 포트 포워딩 외의 모든 권한을 제거했습니다.

결과적으로 앱 설정에 `OPENAI_BASE_URL=http://10.0.0.4:18002/v1` 한 줄만 추가하면 사내 GPU의 강력한 성능을 VPC 내부에서 즉시 사용할 수 있게 되었습니다.

### 2. 0.1%의 오차도 허용하지 않는 RPC Regression Test

또 다른 작업은 메인넷 업데이트(`m113`) 전, RPC 응답의 일치 여부를 확인하는 정밀 감사(Audit)였습니다. 

단순히 "동작한다"가 아니라, **기존 노드(Archive)와 신규 노드의 응답 값이 바이트 단위로 일치하는가**를 증명해야 했습니다. 특히 `debug_traceTransaction` 같은 무거운 메서드는 응답 구조가 복잡해 작은 차이로도 서비스 장애가 발생할 수 있습니다.

**접근 방식:**
실제 인덱서(Indexer)가 호출하는 메서드 리스트를 소스 코드 레벨에서 추출하여 전수 조사를 실시했습니다.

```text
- 인덱서 실호출 목록: getBlock, getTxByHash, getReceipt, call, getBalance, getCode, getTxCount, getRawTxByHash, debug_traceTransaction
- 검증 방법: 동일 블록/트랜잭션에 대해 신구 노드 응답의 md5 해시값 비교
```

**배운 점:**
검증 과정에서 `effectiveGasPrice` 값이 `null`에서 특정 값으로 변경된 케이스를 발견했습니다. 이는 단순한 버그가 아니라 `#106` 수정분으로 인한 의도된 변경임을 확인하며, **"차이(Diff)를 발견하는 것보다 그 차이의 이유를 기술적으로 설명할 수 있는 것"**이 엔지니어링의 핵심임을 다시금 느꼈습니다.

### 마치며

비용을 아끼기 위해 네트워크 경로를 고민하고, 단 하나의 RPC 응답 값 차이를 추적하는 과정이 지루해 보일 수 있지만, 이러한 꼼꼼함이 모여 씨피랩스가 제공하는 서비스의 신뢰도가 됩니다.
