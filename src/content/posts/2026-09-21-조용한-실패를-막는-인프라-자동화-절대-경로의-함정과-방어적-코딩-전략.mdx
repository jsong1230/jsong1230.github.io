# [Dev Log] "조용한 실패"를 경계하라: 인프라 동기화 자동화와 예외 처리의 디테일

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 가장 경계해야 할 상황 중 하나는 시스템이 실패했는데, 그 실패가 '조용히' 일어나는 것입니다. 모니터링 툴이 "정상"이라고 말하고 있지만, 실제 데이터는 동기화되지 않고 있을 때의 그 서늘함은 경험해 본 사람만이 알죠. 

오늘 저는 운영 환경의 데이터 동기화 스크립트에서 발생한 몇 가지 '조용한 실패' 사례를 해결하고, 이를 방지하기 위한 방어적 코딩을 적용했습니다. 그 과정을 공유합니다.

### 1. "어디에 있니?" — 절대 경로의 함정과 환경 독립성

최근 컷오버(Cutover) 이후 EC2에서 실행되던 DB 동기화 크론잡이 죽어 있는 것을 발견했습니다. 원인은 단순했지만 치명적이었습니다. 스크립트 내에서 `REPO_ROOT="$HOME/heritageradio"`라고 경로를 하드코딩해 두었기 때문입니다.

SSH 접속 유저가 `ubuntu`로 바뀌면서 `/home/ubuntu/heritageradio` 경로를 찾지 못했고, 심지어 `.env` 파일들까지 같은 경로에 있어 실패 알림조차 보내지 못하는 '이중 실패' 상태였습니다.

**[해결책]**
사용자 홈 디렉토리에 의존하지 않고, 실행 중인 스크립트 파일의 위치를 기준으로 루트 경로를 잡도록 수정했습니다.

```bash
# 변경 전
REPO_ROOT="$HOME/heritageradio"

# 변경 후: 스크립트 위치 기준으로 동적 결정
REPO_ROOT="${REPO_ROOT:-$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)}"
```

이제 이 스크립트는 어느 서버, 어느 계정에서 실행되든 자신의 위치를 기준으로 경로를 찾습니다. 인프라 환경이 변해도 코드가 깨지지 않게 하는 '환경 독립성'의 기본을 다시금 체감한 순간이었습니다.

### 2. 레이스 컨디션 방지: TTS 합성 중 S3 동기화 스킵

두 번째 문제는 TTS(Text-to-Speech) 합성 과정과 S3 동기화 스크립트가 겹칠 때 발생했습니다. 대량의 오디오 파일을 합성하는 동안 `loudnorm` 같은 정규화 도구가 파일을 `in-place`로 수정하는데, 이때 동기화 스크립트가 파일을 집어 올리면 '잘린 파일'이 운영 서버로 올라가는 문제가 있었습니다.

매번 사람이 `--skip-audio` 옵션을 붙여 수동으로 피하는 것은 근본적인 해결책이 아닙니다. 그래서 **"시스템이 스스로 바쁜 상태(Busy)인지 판단"**하게 만들었습니다.

**[기술적 결정]**
단순히 프로세스 존재 여부만 보는 것이 아니라, Redis 큐의 상태까지 함께 확인하는 보수적인 판정 로직을 도입했습니다.

```bash
tts_busy() {
  # 1. 드라이버 프로세스 확인
  if pgrep -f 'bulk_tts_4week|tts_generate_single' >/dev/null 2>&1; then
    return 0
  fi
  # 2. Redis 큐에 대기 작업이 있는지 확인
  local q
  if ! q=$(docker exec "$TTS_REDIS_CONTAINER" redis-cli llen generate 2>/dev/null); then
    return 0 # 조회 실패는 '모른다' -> 보수적으로 Busy 간주
  fi
  # ... (이하 생략)
}
```

여기서 핵심은 **"모르는 상태는 위험한 상태로 간주한다"**는 원칙입니다. 큐 조회에 실패했을 때 "비어 있다"고 판단하는 것이 아니라 "상태를 알 수 없으니 일단 멈춘다"는 보수적 접근을 택했습니다. 또한, 그냥 스킵하는 것이 아니라 텔레그램 알림을 통해 "왜 스킵되었는지"와 "어떻게 복구하는지(명령어)"를 함께 남겨 '조용한 스킵'을 방지했습니다.

### 마치며: 엔지니어의 인사이트

오늘의 작업들을 통해 다시 한번 느낀 점은, **자동화의 완성은 '정상 동작'이 아니라 '예외 처리'에 있다**는 것입니다.

1. **환경에 의존하지 마라**: `$HOME` 같은 환경 변수보다는 상대 경로와 스크립트 위치 기반의 경로 설정을 지향해야 합니다.
2. **실패는 시끄럽게**: 시스템이 무언가를 건너뛰거나 실패했다면, 반드시 사람이 알 수 있는 채널(Telegram, Slack 등)로 명확한 이유와 해결 방법을 전달해야 합니다.
3. **보수적으로 판단하라**: 분산 시스템이나 비동기 큐를 다룰 때, '알 수 없는 상태'를 '정상'으로 해석하는 순간 장애가 시작됩니다.

작은 쉘 스크립트 하나라도 운영 환경에 올라가는 순간 그것은 '제품'의 일부가 됩니다. 제품 수준의 견고함을 갖추기 위한 디테일한 고민이 결국 시스템의 안정성을 만듭니다.
