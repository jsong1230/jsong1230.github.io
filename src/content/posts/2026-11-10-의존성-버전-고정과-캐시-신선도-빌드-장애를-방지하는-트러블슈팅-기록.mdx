# [Dev Log] 보이지 않는 의존성의 함정과 캐시 신선도(Freshness)의 중요성

안녕하세요, 씨피랩스의 CTO 송주한입니다.

개발자에게 가장 당혹스러운 순간 중 하나는 "어제까지 잘 되던 코드가 갑자기 안 될 때"일 것입니다. 특히 로컬 환경에서는 문제가 없는데, 서버 이미지를 재빌드하거나 배포하는 과정에서 예상치 못한 장애가 발생하면 그 원인을 찾는 데 꽤 많은 에너지를 쓰게 됩니다.

오늘 제가 겪은 두 가지 트러블슈팅 사례를 통해, 인프라 운영과 빌드 시스템에서 놓치기 쉬운 포인트들을 정리해 보려 합니다.

---

### 1. "풀려 있는" 버전의 위험성: Kombu와 Celery 장애

첫 번째 문제는 이미지 재빌드 후 Celery 워커들이 기동되지 않고 무한 재시작되는 현상이었습니다. 로그를 살펴보니 `No module named packaging`이라는 에러가 발생하고 있었죠.

원인은 의존성 관리의 허점이었습니다. `celery[redis]`를 사용하고 있었는데, 그 하위 의존성인 `kombu`의 버전이 명시적으로 고정되어 있지 않았습니다. 운 나쁘게도 재빌드 시점에 `kombu 5.7.0`이 설치되었고, 이 버전이 기존 환경과 충돌을 일으킨 것입니다.

```python
# backend/requirements.txt
celery[redis]==5.4.0
redis==5.2.1
# 2026-11-10: kombu 미고정 상태로 이미지를 다시 빌드하자 kombu 5.7.0 이 들어와
#   `No module named packaging` 으로 celery 워커 3개가 기동 실패했다.
kombu==5.4.2  # Celery 5.4.0과 릴리즈 시기가 유사한 버전으로 고정
```

**인사이트:** 
많은 개발자가 메인 라이브러리의 버전만 고정하면 안전하다고 생각합니다. 하지만 실제로는 전이적 의존성(Transitive Dependencies)에 의해 시스템이 결정됩니다. 특히 프로덕션 환경에서는 `pip freeze`를 통해 모든 하위 의존성까지 락(Lock)을 걸거나, 이번처럼 문제가 된 패키지를 명시적으로 고정하는 습관이 필요합니다.

### 2. 캐시의 역설: "파일이 있으면 맞겠지"라는 믿음

두 번째는 콘텐츠 빌드 시스템에서 발생한 논리적 오류였습니다. S3에서 음성 파일을 가져와 HLS로 빌드하는 과정에서, 동일한 경로에 새로운 파일이 업로드되었음에도 불구하고 빌더가 계속 옛날 파일을 사용하는 문제가 있었습니다.

기존 로직은 단순했습니다. `AUDIO_CACHE_DIR`에 파일이 존재하면 그냥 사용했습니다. 하지만 사용자가 같은 파일명으로 내용을 수정해 다시 올린 경우, 로컬 캐시는 '존재'하지만 '최신'은 아닌 상태가 됩니다.

이를 해결하기 위해 S3의 `head_object`를 이용해 파일 크기와 수정 시각(`LastModified`)을 대조하는 `_cache_is_fresh` 로직을 도입했습니다.

```python
def _cache_is_fresh(cache: Path, key: str) -> bool:
    # ... (중략)
    try:
        head = _get_s3().head_object(Bucket=S3_AUDIO_BUCKET, Key=key)
    except Exception as e:
        # S3 확인 실패 시 빌드를 멈추지 않고 기존 캐시를 사용 (가용성 우선)
        logger.warning("S3 head fail ... 캐시 그대로 사용")
        return True

    st = cache.stat()
    # 크기가 다르거나, 로컬 파일이 S3 원본보다 오래되었다면 False
    if st.st_size != head["ContentLength"] or st.st_mtime < head["LastModified"].timestamp():
        return False
    return True
```

여기서 흥미로운 점은 **성능과 정확도의 트레이드오프**입니다. 매번 S3에 확인 요청을 보내면 네트워크 오버헤드가 발생합니다. 그래서 저는 `_FRESH_TTL_SEC = 600`(10분)이라는 짧은 TTL을 두어, 한 번 확인한 파일은 일정 시간 동안 신선하다고 믿도록 설계했습니다. 또한, S3 API 호출 자체가 실패했을 때 빌드를 중단시키지 않고 캐시를 쓰도록 하여 시스템의 가용성을 확보했습니다.

---

### 마치며

오늘의 작업은 화려한 신기능 구현은 아니었지만, 시스템의 **안정성(Stability)**과 **정확성(Correctness)**을 높이는 중요한 과정이었습니다. 

- **의존성 고정**은 단순한 설정이 아니라 장애 예방을 위한 보험입니다.
- **캐시 전략**을 짤 때는 '존재 여부'뿐만 아니라 '신선도(Freshness)'를 반드시 고려해야 합니다.

작은 디테일이 모여 견고한 시스템을 만든다는 것을 다시 한번 느낀 하루였습니다. 씨피랩스의 엔지니어로서 앞으로도 이러한 '보이지 않는 구멍'들을 메워가는 작업을 계속해 나가겠습니다.
