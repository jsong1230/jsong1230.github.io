# [Dev Log] 불필요한 소음은 줄이고, 신뢰도는 높이는 백업 자동화 전략

안녕하세요, 씨피랩스의 CTO 송주한입니다.

엔지니어로서 시스템을 운영하다 보면 '알림(Alert)'의 딜레마에 빠지곤 합니다. 너무 많은 알림은 결국 '알림 피로(Alert Fatigue)'를 유발해 정말 중요한 장애 신호를 놓치게 만들고, 반대로 너무 적은 알림은 시스템의 침묵 속에 장애가 방치되는 결과를 초래하죠.

오늘은 제가 운영 중인 음성 자산 백업 스크립트를 리팩토링하며, 어떻게 하면 **'신뢰할 수 있는 알림 체계'**를 구축할 수 있을지에 대해 고민한 내용을 공유하려 합니다.

### 1. 문제의 시작: 이름의 혼란과 "거짓 성공"

기존에는 `backup_110_assets_to_s3.sh`라는 스크립트를 사용하고 있었습니다. 여기서 '110'은 과거 서버의 위치를 나타내는 이름이었는데, 최근 인프라를 AWS EC2로 이전하면서 더 이상 유효하지 않은 명칭이 되었습니다. 코드와 인프라의 상태가 일치하지 않으면 유지보수 단계에서 혼선을 주기 때문에, 이를 `backup_audio_assets_to_s3.sh`로 변경했습니다.

하지만 더 심각한 문제는 **'거짓 성공(False Positive)'** 보고였습니다. 
로그를 분석해 보니, 백업 대상 디렉터리가 존재하지 않아 작업을 건너뛰었음에도 불구하고 스크립트는 이를 '정상 완료'로 보고하고 있었습니다.

```bash
# 기존 코드: 소스 디렉터리가 없으면 단순히 skip 하고 완료 처리
if [[ ! -d "$SRC_DIR" ]]; then
  echo "  WARN: ${SRC_DIR} 없음 — skip"
  SUMMARY="${SUMMARY}%0A${asset}: 소스 없음(skip)"
  continue
fi
```

백업 시스템에서 "데이터가 없어서 백업을 안 했다"는 것은 성공이 아니라 **잠재적 장애**입니다. 데이터가 사라졌거나 마운트가 풀린 상황일 수 있기 때문이죠.

### 2. 기술적 결정: 알림의 다이어트와 상태의 기록

이번 작업에서 제가 내린 결정은 크게 두 가지입니다.

**첫째, '정상' 알림은 제거하고 '실패' 알림만 즉시 발송하는 것입니다.**
매일 혹은 매주 오는 "백업 완료" 메시지는 시간이 지나면 무시하게 됩니다. 대신 정상 완료 시에는 텔레그램 메시지를 보내는 대신 `logs/backup_audio_assets.last`라는 상태 파일에 결과를 기록하도록 변경했습니다.

**둘째, '소스 없음'을 명백한 실패(`BACKUP_ERR=1`)로 처리했습니다.**
이제 디렉터리가 없으면 즉시 텔레그램 알림이 발송되어 엔지니어가 즉각 조치할 수 있게 됩니다.

```bash
# 변경된 코드: 소스 없음도 실패로 간주하여 즉시 알림 유도
if [[ ! -d "$SRC_DIR" ]]; then
  echo "  ${asset}: 소스 없음 (${SRC_DIR})"
  BACKUP_ERR=1
  SUMMARY="${SUMMARY}%0A${asset}: ⚠️소스 없음"
  continue
fi
```

### 3. 인사이트: 통합 대시보드(Digest)의 힘

정상 알림을 없애면 "정말 잘 돌고 있는 건가?" 하는 불안함이 생깁니다. 이를 해결하기 위해 `daily_monitor_digest.sh`를 활용했습니다. 

개별 스크립트가 보내는 파편화된 알림 대신, 매일 아침 08:30에 전날의 주요 작업 상태를 한 줄로 요약해서 받는 **'Daily Digest'** 방식을 채택한 것입니다. 만약 상태 파일의 기록이 8일 이상 없거나 실패 기록이 있다면, 그때는 강력한 경고를 보내도록 설계했습니다.

### 마치며

이번 작업은 단순한 스크립트 수정이었지만, 운영 관점에서는 **'소음(Noise)을 줄이고 신호(Signal)를 강화'**하는 중요한 과정이었습니다. 

기술적 화려함보다 더 중요한 것은 "내가 믿고 잠들 수 있는 시스템인가"에 대한 확신입니다. 씨피랩스에서도 이러한 디테일한 운영 철학을 바탕으로 더 견고한 Web3 및 AI 인프라를 구축해 나가겠습니다.
