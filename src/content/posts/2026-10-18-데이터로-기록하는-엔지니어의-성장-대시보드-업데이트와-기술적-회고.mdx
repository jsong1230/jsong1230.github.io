## [Dev Log] 데이터의 흐름으로 기록하는 엔지니어의 일상: 대시보드 업데이트와 기술적 회고

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

엔지니어에게 있어 '기록'은 단순히 과거를 남기는 것이 아니라, 현재의 상태를 진단하고 미래의 방향성을 결정하는 중요한 데이터셋이 됩니다. 저는 개인적으로 제가 관리하는 여러 프로젝트의 활동량을 시각화한 대시보드를 운영하고 있는데, 오늘 그 데이터를 최신화하며 몇 가지 흥미로운 지점들을 발견했습니다.

### 🛠️ 오늘의 작업: 대시보드 데이터 동기화

오늘 진행한 작업은 간단해 보이지만 의미가 큽니다. `src/data/dashboard.json` 파일을 업데이트하여 현재 제가 집중하고 있는 리포지토리들의 활동 지표(commits_7d, commits_30d)와 최신 커밋 메시지를 반영하는 작업이었습니다.

```json
// 변경 전
"name": "heritageradio",
"last_msg": "[main] fix(prefetch): 음성 칸에 episode 가 없으면 공백으로 — 평�",

// 변경 후
"name": "key-backup-server",
"last_msg": "build: pin test dependency org.web3j:crypto to 4.8.7",
"branch": "build/pin-web3j-java8",
```

단순한 JSON 업데이트처럼 보이지만, 이 diff 속에는 최근 제가 씨피랩스에서 고민하고 있는 기술적 결정들이 고스란히 담겨 있습니다.

### 💡 기술적 결정과 인사이트: 'Pinning'의 중요성

특히 눈에 띄는 부분은 `key-backup-server` 리포지토리의 커밋 메시지입니다: 
`"build: pin test dependency org.web3j:crypto to 4.8.7"`

Web3 및 블록체인 인프라를 다루는 엔지니어로서 제가 가장 경계하는 것 중 하나가 바로 **'의존성 라이브러리의 예기치 못한 업데이트'**입니다. 특히 암호화 라이브러리(`web3j:crypto`)의 경우, 버전 하나 차이로 서명 방식이나 키 파싱 로직이 미세하게 변할 수 있고, 이는 곧바로 서비스 장애나 심각한 보안 사고로 이어질 수 있습니다.

이번에 특정 버전을 명시적으로 고정(Pinning)한 이유는 다음과 같습니다.
1. **재현 가능성(Reproducibility):** 어떤 환경에서 빌드하더라도 동일한 바이너리가 생성되어야 합니다.
2. **안정성(Stability):** 검증되지 않은 최신 버전이 자동으로 배포 파이프라인에 유입되는 것을 방지합니다.
3. **하위 호환성 유지:** 특히 Java 8 환경을 유지해야 하는 레거시 시스템과의 호환성을 보장하기 위함입니다.

### 🚀 마치며: 시스템의 '스냅샷'을 남긴다는 것

오늘 업데이트 내역을 보면 `prod-snapshot/20261017`과 같은 브랜치들이 많이 보입니다. 저는 운영 환경에 배포되는 시점의 코드를 스냅샷 형태로 관리하는 습관을 가지고 있습니다. 문제가 발생했을 때 "그때 정확히 어떤 코드가 돌고 있었는가"를 즉각적으로 확인하는 것이 복구 시간을 단축하는 가장 빠른 길이기 때문입니다.

20년 넘게 엔지니어로 일하며 깨달은 점은, 화려한 최신 기술보다 더 중요한 것은 **'예측 가능한 시스템'**을 만드는 것이라는 점입니다. 라이브러리 버전을 고정하고, 배포 시점의 스냅샷을 남기는 이러한 작은 습관들이 모여 거대한 시스템의 안정성을 구축합니다.

내일은 또 어떤 데이터가 제 대시보드를 채우게 될까요? 기록하는 즐거움과 함께 성장을 이어가겠습니다.
