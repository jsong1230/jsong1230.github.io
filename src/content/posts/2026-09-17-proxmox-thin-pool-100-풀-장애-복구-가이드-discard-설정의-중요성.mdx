# [Troubleshooting] Proxmox Thin Pool 100% 장애 복구와 'Discard'의 중요성

안녕하세요, 씨피랩스의 CTO 송주한입니다.

개발자라면 누구나 한 번쯤 겪는 상황이 있습니다. 분명 서버의 디스크 사용량(`df`)은 여유가 있는데, 정작 서버는 '쓰기 불가' 상태가 되어 뻗어버리는 경우죠. 오늘 새벽, 제가 관리하는 dev 서버(110번)에서 정확히 이 현상이 발생했습니다. 

단순한 서버 다운인 줄 알았으나, 파고 들어가 보니 하이퍼바이저 레벨의 스토리지 관리 이슈였습니다. 오늘은 이 장애의 원인과 해결 과정, 그리고 인프라 운영에서 놓치기 쉬운 기술적 포인트에 대해 공유하고자 합니다.

### 1. 현상: "분명히 살아있어야 하는데, 모든 길이 막혔다"

새벽 2시 31분경, 110번 서버가 완전히 불통되었습니다. SSH, Tailscale, Cloudflare Tunnel까지 모든 연결이 끊겼고 `ping`조차 응답하지 않는 상황이었습니다. 

처음에는 물리 서버의 전원 문제나 네트워크 장애로 판단해 "원격 복구가 불가능하다"고 생각했습니다. 하지만 다시 점검해 보니 이 서버는 물리 서버가 아니라 **Proxmox VM(pve-06 / VMID 103)**이었고, 하이퍼바이저는 멀쩡히 살아있었습니다. 여기서부터 진짜 원인을 찾는 추적이 시작되었습니다.

### 2. 원인 분석: Thin Pool의 함정

하이퍼바이저 로그를 확인하니 범인은 **Thin Pool 100% 점유**였습니다.

```text
02:30:44 WARNING: Thin pool vmdata-vmpool-tpool data is now 100.00% full
02:31:42 thin: switching pool to out-of-data-space (error IO) mode → VM 정지
```

더 흥미로운 점은 게스트 OS 내부의 디스크 사용량은 **73%(718G/995G)**였다는 것입니다. OS는 공간이 남았다고 생각하지만, 실제 물리 저장소인 Thin Pool은 꽉 차서 더 이상 데이터를 쓸 수 없는 `io-error` 상태가 되어 VM이 안전하게 정지된 것이었습니다.

**왜 이런 괴리가 발생했을까요?**
원인은 `scsi0` 설정에 `discard=on` 옵션이 누락되었기 때문입니다. 게스트 OS에서 파일을 삭제해도, 하이퍼바이저(QEMU)가 이를 인지하고 물리 공간을 회수(Discard)하지 않아 '유령 공간'이 계속 쌓였던 것입니다.

### 3. 해결 과정: 부팅 전 '강제 회수'가 핵심

풀이 100% 찬 상태에서 단순히 VM을 켜면, 부팅 과정에서 발생하는 쓰기 작업 때문에 다시 `io-error`가 발생합니다. 따라서 **부팅 전에 호스트 레벨에서 공간을 먼저 확보**하는 전략을 택했습니다.

가장 까다로웠던 점은 `mount -o offset=` 방식으로는 `discard` 작업이 지원되지 않는다는 것이었습니다. 결국 `dmsetup`을 이용해 리니어 매핑을 생성한 뒤 `fstrim`을 수행했습니다.

```bash
# 핵심 복구 명령어 흐름
dmsetup create vm103p1 --table '0 2152724447 linear /dev/vmdata/vm-103-disk-0 2099200'
mount /dev/mapper/vm103p1 /mnt/vm103
fstrim -v /mnt/vm103  # → 268.1 GiB 회수 성공!
```

이 과정을 통해 약 **268GiB의 공간을 즉시 회수**했고, pool 사용률을 100%에서 81%로 낮춘 뒤 VM을 정상 기동시켰습니다. 복구 시간은 단 7분이었지만, 원인을 정확히 짚어내지 못했다면 물리 서버를 직접 재부팅하는 헛수고를 했을 것입니다.

### 4. 인사이트 및 교훈

이번 장애를 통해 세 가지 중요한 교훈을 얻었습니다.

1. **인프라 설정의 디테일**: 가상화 환경에서 Thin Provisioning을 사용한다면, 게스트와 호스트 양쪽 모두에서 `discard` 옵션이 활성화되어 있는지 반드시 확인해야 합니다. (이미 pve-04에서도 유사 사례가 있었음을 깨닫고 클러스터 전수 조사를 결정했습니다.)
2. **가시성(Visibility)의 부재**: VM 내부의 `df`만 믿어서는 안 됩니다. 하이퍼바이저 레벨의 LVM Thin Pool 사용률을 모니터링하고 알림을 받는 체계가 필요함을 절감했습니다.
3. **정확한 진단의 힘**: "원격 복구 불가"라는 성급한 결론 대신, 인프라 계층(물리 $\rightarrow$ 하이퍼바이저 $\rightarrow$ VM)을 하나씩 짚어가는 디버깅 습관이 복구 시간을 획기적으로 줄여줍니다.

기술적인 깊이는 결국 이런 '사소한 설정 하나'가 만드는 결정적인 차이에서 온다고 생각합니다. 씨피랩스의 인프라를 더 견고하게 만들기 위해, 이번 사례를 문서화하고 전 노드 점검을 진행할 예정입니다.
