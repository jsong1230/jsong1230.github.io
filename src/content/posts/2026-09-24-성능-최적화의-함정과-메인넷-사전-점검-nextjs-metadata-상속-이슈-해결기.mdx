# [Dev Log] 성능 최적화의 함정과 메인넷 사전 점검: 1.9초를 0초로 만드는 법

안녕하세요, 씨피랩스의 CTO 송주한(Jeffrey Joo-Han Song)입니다.

오늘은 프론트엔드 성능 최적화 과정에서 겪은 예상치 못한 '상속의 함정'과, 메인넷 롤링 업데이트를 앞둔 긴장감 넘치는 사전 점검 작업을 진행했습니다. 엔지니어로서 늘 마주하는 '당연하다고 생각한 전제'가 어떻게 버그로 이어지는지, 그리고 인프라 레벨에서 어떤 디테일을 챙겨야 하는지에 대한 기록을 남겨봅니다.

---

### 1. Next.js의 Metadata 상속 함정: "DRY가 항상 정답은 아니다"

최근 랜딩 페이지의 링크 미리보기(OG Image) 속도가 느리다는 점을 발견했습니다. ALB 액세스 로그를 분석하니, 크롤러의 요청 중 69%가 `/opengraph-image`였고 응답에 최대 2초가 소요되고 있었습니다. 

원인은 `app/opengraph-image.tsx`를 통한 **동적 이미지 생성**이었습니다. 내용은 고정되어 있는데 매 요청마다 렌더링을 하고 있었죠. 저는 이를 정적 파일(`.png`)로 교체하고 동적 생성 파일을 제거하여 응답 시간을 '즉시'로 최적화했습니다.

그런데 여기서 문제가 발생했습니다. 파일을 제거하자 랜딩 페이지의 OG 이미지가 통째로 사라진 것입니다. 코드에는 다음과 같은 주석이 있었습니다.
`// images 는 layout.tsx 에서 상속 (DRY)`

**하지만 Next.js의 동작 방식은 제 생각과 달랐습니다.** `page.tsx`에서 `openGraph` 객체를 정의하면, `layout.tsx`의 값을 필드 단위로 병합(Merge)하는 것이 아니라 **객체 전체를 교체(Replace)** 합니다. 즉, `images` 필드를 명시하지 않으면 레이아웃의 설정은 완전히 무시됩니다.

그동안 문제가 없었던 이유는 `opengraph-image.tsx`라는 파일 규약이 메타데이터 설정과 무관하게 이미지를 강제로 주입하고 있었기 때문입니다. 최적화를 위해 파일을 지우자, 숨어있던 설정 누락이 드러난 것이죠.

**💡 인사이트:** 
프레임워크의 '마법' 같은 기능(파일 기반 규약)은 편리하지만, 때로는 잠재적인 결함을 가리는 가림막이 되기도 합니다. 특히 상속이나 병합 로직이 포함된 설정에서는 "당연히 되겠지"라는 전제보다 공식 문서의 동작 방식을 다시 확인하고, 중요한 설정은 명시적으로 선언하는 것이 안전합니다.

### 2. 메인넷 사전 점검: 인스턴스 스토어의 위험성

다른 한편으로는 메인넷 롤링 업데이트를 위한 Phase 0 사전 점검을 수행했습니다. 14대의 노드를 전수 조사하며 가장 중요하게 확인한 것은 **데이터 저장소의 실체**였습니다.

EC2 `describe-instances` 결과, 모든 노드가 `RootDeviceType=ebs`였고 추가 EBS 볼륨이 없음을 확인했습니다. 이는 곧 체인 데이터가 **인스턴스 스토어(Local NVMe)**에 저장되고 있다는 뜻입니다.

```text
★14대 전부 인스턴스 스토어 확정 
⇒ 롤링 중 EC2 stop/start·reboot 금지. 프로세스 재시작만 한다. 
인스턴스가 내려가면 chaindata 가 사라진다.
```

인스턴스 스토어는 성능은 압도적이지만, 인스턴스를 중지(Stop)하거나 재부팅(Reboot)하면 데이터가 영구적으로 소실되는 휘발성 특성을 가집니다. 따라서 이번 롤링 업데이트 전략은 '인스턴스 접촉 금지, 프로세스 원자적 교체'로 확정했습니다.
