## [Dev Log] 데이터의 흐름으로 기록하는 나의 성장 궤적

안녕하세요, 씨피랩스(CP Labs)의 CTO 송주한입니다.

엔지니어로서 20년 넘게 코드를 작성하며 제가 깨달은 것 중 하나는, 단순히 '기능을 구현하는 것'보다 '어떻게 기록하고 추적하는가'가 장기적인 생산성에 더 큰 영향을 미친다는 점입니다. 우리는 흔히 Git 커밋 로그를 통해 작업 내용을 확인하지만, 수십 개의 레포지토리를 운영하다 보면 내가 최근 어디에 집중했는지, 어떤 리듬으로 개발하고 있는지 한눈에 파악하기 어렵습니다.

그래서 저는 개인 대시보드를 통해 저의 개발 활동 데이터를 시각화하여 관리하고 있습니다. 오늘은 그 대시보드의 기반이 되는 `dashboard.json` 데이터를 업데이트하는 작업을 진행했습니다.

### 단순한 데이터 업데이트, 그 이상의 의미

오늘의 작업은 겉보기에 단순한 `chore: Update dashboard data`였습니다. 하지만 이 JSON 파일이 담고 있는 내용은 제 개발 라이프사이클의 '스냅샷'과 같습니다.

```json
// src/data/dashboard.json 변경 부분
{
  "generated_at": "2026-08-19T23:00:02.032Z",
  "machines": [
    {
      "name": "gram-jsong",
      "repos": [
        {
          "name": "claude-agent",
          "last_msg": "docs: 8/19 morning sweep, 151 rewind status, packages cleanup, validator docs ar",
          "activity": [13, 6, 3, 3, 2, 1, 0],
          "commits_7d": 35,
          "commits_30d": 288
        },
        ...
      ]
    }
  ]
}
```

이번 업데이트에서 흥미로운 점은 `claude-agent` 레포지토리의 활동성입니다. 최근 30일간 288개의 커밋이 기록되었는데, 이는 제가 최근 AI 에이전트의 자율성과 검증 프로세스 최적화에 얼마나 깊게 몰입하고 있는지를 수치로 보여줍니다. 반면 `booksummary`와 같은 개인 프로젝트는 간헐적인 활동 패턴을 보이며, 일과 삶의 균형을 어떻게 맞추고 있는지도 투영됩니다.

### 기술적 결정: 정적 데이터 기반의 대시보드

왜 굳이 실시간 API가 아닌 JSON 파일을 업데이트하는 방식을 택했을까요? 

첫째는 **성능과 비용**입니다. 개인 대시보드는 초고속 실시간성이 필요하지 않습니다. 하루 한 번의 스냅샷만으로도 충분한 인사이트를 얻을 수 있으며, 정적 파일로 관리하면 GitHub Pages와 같은 환경에서 별도의 서버 비용 없이 매우 빠르게 렌더링할 수 있습니다.

둘째는 **이력 관리(Versioning)**입니다. JSON 파일을 Git으로 관리하면, 시간이 흐른 뒤 "내가 6개월 전에는 어떤 프로젝트에 시간을 쏟았지?"라는 질문에 대해 `git diff`만으로 명확한 답을 얻을 수 있습니다. 데이터 자체가 버전 관리 시스템의 일부가 되는 셈입니다.

### 마치며: 메타 인지의 도구로서의 개발

씨피랩스에서 수많은 프로젝트를 리딩하며 제가 팀원들에게 항상 강조하는 것은 '측정 가능한 성장'입니다. 내가 무엇을 했는지 기록하고, 그것을 시각화하여 바라보는 과정은 일종의 '메타 인지' 과정입니다. 

단순히 코드를 짜는 행위를 넘어, 나의 활동 데이터를 객관적으로 바라볼 때 비로소 다음 단계로 나아갈 방향이 보입니다. 여러분도 자신만의 '성장 대시보드'를 만들어보시는 건 어떨까요? 

작은 기록들이 모여 결국 거대한 전문성을 만든다는 믿음으로, 내일도 기록하고 성장하겠습니다.
